# 自己対局後の長考研究・世代学習：再発防止計画（案）

作成日：2026-10-21。対象：KUMOJI 雲路、研究PR #290。**本ファイルは実行計画であり、修正・再実行・強化達成の証拠ではない。** 正式版 main v2.0.21 と採用済み局面知識は変更しない。

## 0. 今回の事実と失敗点

- 依頼は2026-10-20 22:53〜10-21 04:53 JSTの6時間を使い、対局だけでなく再分析・学習・新旧比較・研究世代継承まで進めること。
- 既存300局（run 39437543483）と研究用100局（run 39442078235）が完了。後者は同一正式版同士の53対47、違法対局0であり、強化の証拠ではない。
- controller run 39441941187 は、100局から10,987異局面、96選別局面を解析（49件の局面知識候補、探索研究候補4件、保留42件、混在1件）。 `learning_status: not_run`。
- `tools/research/postgame_progress.py` が原局から作る研究課題数と、`tools/research/postgame_followup.py` の `POLICY_FOLLOWUP.max_tasks=8` が不整合。後者の `tasks_from` が `ValueError: follow-up budget exceeded; review rather than truncate` を投げ、第1世代のprepare段階で停止。
- 単発確認タイマーも途中で無効化され、期限まで復旧・報告へ接続できなかった。**実際に試した時間と、ユーザーが与えた6時間は異なる。**
- Release `records-2026-10-01` に `spiral-sixhour-strength-20261020-01-state-000008.json` と source packageを含む途中原本が存在する。Actionsの期限付きartifactもある。新たな研究では読戻しhash・原本・手・先後・設定を検証して再利用する。

## 1. 優先順位：「どれだけ対局したか」より「前世代より何を学んだか」

一つの研究世代を、(A)新規・再利用した自己対局原本、(B)敗因候補抽出、(C)時間を掛けた自作探索、(D)学習候補への具体反映、(E)独立対局、(F)研究親の継承／維持、の完了単位で扱う。

分析時間を削って対局数を稼がない。次の6時間枠の目安は、対局・原本生成10〜15%、疑問手の抽出と長考研究45〜55%、候補実装・学習15〜20%、独立比較15〜20%、保存・障害復旧10%。本配分は**計画値**であり実測・新しい指示に応じて変更する。残り時間が足りなければ対局を追加せず長考と検証、成果物保全を優先する。

## 2. 棋譜からの選別と時間を掛けた検討

1. 全実戦手の評価急変、詰みの見落とし、駒損、受けの不備、探索の不安定さ、同型の悪手再発、読み筋の不一致を抽出。評価急変だけを「疑問手確定」とみなさない。
2. 自分の局面復元・相手応手・手番・反復履歴・エンジン設定を固定。局単位／類似局面群単位で訓練・検証・未使用評価集合を分離。外部AIを教師にしない。
3. 原則一世代8〜24件を詳しく読む。重要度（評価急変、再発頻度、未解決度、学習経路があるか）で優先順位を付け、優先外は全件IDと理由を次回へ保存。異なる序盤・中盤・終盤／先手・後手を確保。
4. 自作探索で一度目5秒、二度目30秒、最重要・不安定局面は60〜120秒程度まで予算を伸ばして読む。これは新しい研究設定の案であり、既定の200ms対局設定は変更しない。元手と有力な代替手それぞれの**相手の最善候補の応手**を検討し、子局面を同条件の固定深さで比較する。必要なら読みの反復・詰みの合法な証明を行う。
5. 探索深さ、総節点数、主変化、各候補手の評価推移、時間、反復での一致度、根拠原本を研究記録へ保存。不一致／時間切れ／実力で解決不能は「未確定」と記録し、誤って教師データにしない。長考で選んだ手すべてを正解として学ばない。
6. 例: 28歩打がただで取られる等の局面は、直前の探索の枝刈り・駒得評価・王手／詰めろの読落とし・相手応手への評価伝播を分類してから改善方法を決める。

## 3. 改善反映先は9配点に限定しない

- **探索**: 候補手順、静止探索、詰み確認、危険な歩打・駒損の検証、相手応手の枝刈りなど。探索量・読む順序・実際の手変化を証拠にする。
- **評価**: 玉の安全、持駒価値、利き、連携、危険手など。大きな変更を一括混入せず、疑問手の機序に対応した単独変更候補を検証。9配点の小変更だけで済ませたことにしない。
- **局面知識**: 条件付き研究手と後続読み筋、root探索順の改善、類似局面への適用条件。反復・合法性・版一致を照合し、研究局面以外への誤適用は防ぐ。
- **次の訓練データ**: 再発パターン・未解決局面を次の対局／研究の重点へ戻す。勝者の全着手を教師にしない。
- 一世代の主要な比較は単一機序（または事前に固定した比較群）とし、変化の原因が検証できるようにする。研究親としての更新は試験条件合格時のみ、正式Engineへの昇格はR10に従う。

## 4. 上限超過と途中停止への再発防止（実装が必要）

- `tasks_from` は最初に**全課題ID・種別・優先度・上限・必要時間見積り**を確定して保存する。後続最大8件は「1バッチで処理する件数」として扱い、超過分を破棄・無断打切り・一括例外にしない。8件単位に分け、残りを期限・優先度付き永続キューへ残す。
- 各バッチの開始前に対象taskの実装経路と予算を検査する。未実装の課題種別は別途未実装として保留し、関連のない対局で代用しない。毎バッチ後に対象ID、試した探索、成果、除外理由、残件数をチェックポイント保存。
- **永続化**: 原本/バージョン/seedを保存済みReleaseからhash検証、研究はケースごと（多くとも数件ごと）に重複排除可能なID付きcheckpointを保存する。controller内部の一時チェックポイントだけで成功と扱わない。再開時は成功済みIDを二度実行しない。
- **復旧**: 旧controllerの`state-000008`・成功した100局を保持し、旧PLANとアルゴリズムのSHAを勝手に書き換えず、修正コードに対応した**新たな明示的復旧計画**を作る。実行済みゲーム・既処理seed・訓練/検証split・親・記録hashを引き継ぐ。旧runの失敗履歴を残す。
- **事前CI**: 96局面から8件超の研究課題が生じるfixtureと、8/9/96件・不正な課題・未実装種別・5件終了後クラッシュ/復旧・重複起動・期限到来の試験を追加。研究原本保存と照合までスモークを通す前に大規模起動しない。
- **安全**: 以前安全性チェックで拒否されたG2専用Workflow改変は別経路で迂回しない。許可された既存の入口・変更のみを使う。

## 5. 実戦での検証・次世代への継承

候補Aと親Bの両方で、採用済み局面知識、`go movetime 200`、条件付き長考、先後、初手条件を揃える。100局程度は異常や方向を見る選別、別seedで200局以上を確証候補の確認とし、95%区間・棋譜重複・違法手0・使用した改善機能（知識一致、探索量、読み筋分岐、局面別の改善）を確認。必要ならさらに局数を増やす。95%下限が50%を超えない場合は強化確定と報告しない。独立局面で悪化した場合も記録。

強化候補が明確に勝ち越した場合だけ**研究上の親モデル**を更新して、次世代の原本生成・課題分析へ進む。合格候補がなければ親を維持し、再検討の仮説を更新する。無理に世代数を積み上げない。本人の採用判断があるまでmain/版名/正式知識は変更しない。

## 6. 6時間の管理方法

- GitHub側の固定研究計画に開始時刻・締切時刻・最大対局数・解析時間予算・各工程の証拠・停止条件を持たせる。ChatGPTタイマーの発火だけを研究継続の条件にしない。
- 重いGitHub Actions処理が始まったら、controller側は工程終了ごとに次工程へ進み、期限前に新しい長時間jobの起動を止め、少なくとも最後の20〜30分を証拠の保存・要約へ割く。
- ChatGPTの確認タイマーは**同じ1本の単発予定**のみ。起動・検査時点の実測ETAへ更新し、未完了・失敗なら実行記録を読んで、許された修復または未完の具体的な報告につなぐ。タスクを一度でも勝手に無効化しない。6時間の明示期限を超えた研究継続も無断で行わない。
- 終了時の4分類：`completed_and_verified` / `blocked_with_saved_state` / `deadline_partial` / `safety_blocked`。未完了を成功や「6時間学習実施」と報告しない。

## 7. 作業順と完了基準

1. **復旧前検査**: state-000008と全棋譜の長期原本をhash再取得・照合。直近100局の実戦手が欠けないか検査。
2. **実装修正**: 上限超過の分割キューと優先度・再開永続化。元の8件上限やアルゴリズムの固定性を説明なく変更しない。
3. **小規模CI実証**: 8件超を持つ実データ相当で2バッチ以上進むこと、保存後クラッシュで二重計算しないこと、未実装の扱い、保存読戻しを証明。
4. **長考研究**: 保存済み原本の高リスク手を選び、少なくとも重要な数件を5秒→30秒→60秒以上で再探索。研究記録を残す。
5. **候補生成・比較**: 少なくとも1種類の具体的改善候補を用意、独立対局で親と比較、機能が実際に動いたか検証。強化未確認なら採用せず課題として残す。
6. **一世代完了**: 原本→詳細研究→反映先→独立検証→親を継承/維持の**全リンクに実測証拠**があること。締切時には未完了リンク、研究成果、次回再開ID、必要な修復を明示する。
