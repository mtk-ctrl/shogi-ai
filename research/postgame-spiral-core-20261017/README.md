# 自己対局から次の世代へ返す中核

正式Engineではなく、選別・学習提案・研究世代の判断を行う研究基盤である。[PLAN](PLAN.md) と [実測](RESULTS.md) を参照する。

## 改善を返す先

| 対局後に分かったこと | 返す先 | 進めない条件 |
|---|---|---|
| 長く読むと改善するが静的順位は既に妥当 | 探索の問題集 | 評価重みをその例だけで変えない |
| 現在の親が誤り、厳密な自作対比較と静的順位が逆 | 小さな評価重み候補 | 独立群不足・検証悪化・実Engineで効果なし |
| 確認した研究手を親が選べない | 分離した候補知識 | 検証/未使用群を記憶しない。対象で修正なし・実戦利用0なら強化認定しない |
| 親が既に同じ手を指す | 改善済みの記録 | 新しい改善として水増ししない |
| 欠損・不安定・反復・原因不明 | 保留と追加材料の要求 | 無理に教師ラベルを作らない |

勝利は着手前局面への長期結果。研究手を指した場合の結果は観測していないため、元の勝敗を研究手の後へ貼らない。順位学習は「どの重みを増減すれば実戦手より改善手の相対評価が上がるか」を微小な変更で提案する。合法手を禁止したり、実戦中に報酬点を足したりする処理ではない。

## 実装入口

- `tools/research/postgame_spiral.py`：選別済み診断の完全履歴・厳密値・分割台帳を照合し、固定親を200msで2回再検査する。適格なデータだけ学習器へ渡す。新しい学習済み候補がなければ材料不足を返す。
- `tools/research/postgame_ranker.py`：1候補・既存9軸・親から±5%以内の評価重みを提案する。正式値ではなく候補のUSI options JSONを生成する。各次世代の研究親の値から更新し、毎回正式版の値へリセットしない。
- `tools/research/postgame_cycle.py`：予算・固定親・候補hash・操作ID・実開始・保存証拠を照合する。CLIは `init / request / started / finish / eta`。状態更新は読み出したファイルのSHA256を指定して比較更新する。

状態の流れは、準備→実Engine検査→選別100局→条件通過時だけ確認200局→研究上の親を選択→予算内なら次回用原本→次の準備。材料不足や候補不合格でも、親を保持して次の材料へ戻れる。世代数・総局数が尽きれば停止する。上限は開始前のplanへ固定する。正式採用・main Engine変更はこの流れに含めない。

分割台帳は次世代へ引き継ぐ。訓練/検証/未使用をまたぐ新しい連結や、一度成績を見た未使用群は隔離する。例数を増やすために同じ局面を複製しない。

## 実行例と未接続部分

準備器は `python3 tools/research/postgame_spiral.py --help`、制御CLIは `python3 tools/research/postgame_cycle.py --help` で入力を確認できる。依存は既存の `python-shogi==1.1.1`。第2世代以降の準備には前回の `split_registry` を別JSONとして渡し、親の評価設定も渡す。診断側と設定が異なる場合は拒否する。

制御のreceiptは信頼された実行・監査アダプターから受け取る契約であり、JSONにtrueと書けば監査したことになるわけではない。既存のG1専用起動器は固定条件のまま維持した。今回のコードだけでGitHub dispatch・Release移送・タイマー登録・多世代の実働が自動実行されるとは扱わない。

残る接続は、研究親のパラメータ/知識を反映した汎用の再分析・候補materialize・実Engine検証と、既存対局/保存/監査への実行アダプターである。GitHub APIで実空きを取得し、起動入口→本体→実開始→保存をこの台帳へ渡す。タイマー用のETA算出は実装したが、APIへの登録・同一タスク更新はアダプター側の責任として残る。既存G1の安全性制約を別経路で実現するためにこの制御を使わない。

この中核は、単体・合成例と保存済み実データの準備検査まで検証済み。自動多世代の棋力向上を実証したものではない。
