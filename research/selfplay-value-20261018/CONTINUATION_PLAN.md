## 5工程と、通常3か所の終了確認

有効な確認タスクは全体で1本。5工程ごとに5本のタイマーを作る方式ではない。重い処理3か所で同じ一回限りタスクの実行時刻を更新する。短い工程は同じ発火内で処理し、長引くと判明したときだけ実進捗に基づく終了見込みへ更新する。

## 時刻の具体例（予約そのものではない）

19対局runnerを使えて10:00に工程1を開始する仮例:

1. 10:15に同じタスクを設定。発火時に原本生成・監査・保存を確認し、短い工程2を続ける。
2. 10:18に工程3を開始できた場合、同じタスクを10:42へ更新する。候補3件の100局比較はActionsが順に実行し、候補ごとの別タイマーは作らない。
3. 10:42に選別結果・保存を検査し、適格なら工程4を開始。同じタスクを11:22へ更新する。
4. 11:22に確認結果を監査し、11:25までに工程5を完了できた場合、次の親同士の300局を開始し、同じタスクを11:40へ更新する。
5. 11:40に次世代の工程2へ戻る。

発火が遅い場合やActionsが先に進んだ場合、仮の時刻を守るために待機しない。実際の工程を照合し、完了済みなら次へ進む。予定時刻にまだ未完了なら、原因・残局数・最終runner・集約/保存の状態から新しいETAを計算する。固定間隔の再確認や短いタイマーを連打する運用へ置き換えない。

## 次世代への具体的な接続

合格の場合:
候補Cを固定 → 親P対Cの1000局と保存を検証 → 研究親の参照をCへ更新 → C対Cの新規300局 → Cの9配点で再分析/特徴量照合 → Cからの差分として学習 → 次の3候補 → Cを比較相手に選別・確認する。

不合格の場合:
親Pを保持 → 不合格の原因と使用済み検証を記録 → P対Pで新しいseedの300局 → 新しい材料から別の候補を作る。同じ候補の再確認や、見た結果を受けた閾値緩和で合格にしない。候補がゼロ、学習提案不適格、選別で全候補50%未満の場合も1000局を起動せず同じ扱いとする。対局・監査・保存の技術的不具合は研究上の不合格と数えず、許可された修復と同一操作の照合を行う。

研究ラウンド番号と、合格して更新された親の世代番号は別に記録する。不合格ラウンドで親を強くなった新世代として数えない。研究親の更新は、正式main Engineへの採用と区別する。

引継ぎ対象は、固定Engine commit・両側の実バイナリhash・親の9配点・知識hash・学習モデルhash・元棋譜とRelease receipt・学習/選択/検査の分割台帳・使用済みseed/検証群・操作ID/run ID・残予算・確認タスクID・次工程とETA。毎回正式配点へ戻さず、更新した親を学習と対局の両方に渡す。異なる親や別世代の古い静的評価は上書き転用しない。

分割は既存の局単位70/15/15を基礎とし、同一棋譜・同一局面の既知の連結が群をまたぐものを隔離する。現行学習器の世代内除外だけで、世代をまたぐ混入対策まで完了と扱わない。継続台帳で、過去に見た評価用データを未使用と再表示しない。診断8局面の再分析結果を正解ラベルとして追加せず、比較1000局をその候補の訓練・選択へ戻さない。勝敗は局面の勝敗確率の観測に使い、個々の着手の正解証明にはしない。

各世代の95%区間を、反復全体の95%保証や幅広い初期局面での独立性の証明とは呼ばない。複数世代から良い結果だけ選ぶ問題と親からの累積差分を結果へ明記する。正式採用の判断前には、最終候補を固定したうえで初期の正式版との新しい比較計画を別に作る。その比較や自動正式採用は今回の予算へ黙って追加しない。

## 実行担当と重複防止

- GitHub側は、各まとまり内の候補対局・集約・全手監査・Release保存を完了順に進める。
- 確認タスク側は、状態と証拠を読み戻し、必要な軽量処理・次のまとまりの起動・同じタスクのETA更新を担当する。
- 親の更新と次世代起動の責任は一つの制御入口へ集約し、既存の単一サイクル制御とタイマーが別々に次300局を起動しない。
- 状態には loop_id、round_id、parent_id、phase、operation_id、frozen_input_hash、intent/run/attempt、publication、task_id、ETA根拠、remaining_budget、stop_requested、revision を保存する。
- 操作IDは循環/ラウンド/工程/固定入力hashから作る。意図保存後に起動し、応答不明なら既存要求/runを照合する。状態更新は直前に読んだrevisionとの比較更新にする。
- すべての起動経路を同一の直列化に通し、別runを強制中断しない。未完了runがあれば追跡を優先する。
- 完了条件を満たした保存がなければ親を更新しない。親を更新しただけで次の300局の開始成功と扱わない。
- タイマー登録/更新の応答と、保存したtask_id・次回時刻を照合する。登録に失敗したら、継続予約済みとは報告しない。

## 初回の連続接続試験の範囲

今回の保存済み300局・3候補から再開する場合は、まず親の更新判定を2回まで行い、判定後の次回用300局・再学習まで確認する計画とする。新規対局は最大2×(選別300+確認1000+次回用300)=3,200局。2回とも進行条件に届かなければ、2回目後の追加300局は起動せず、親を保持して停滞の原因と次の仮説を保存する。

2回の判定と必要な引継ぎ保存・読み戻しが完了したら報告してタイマーを停止する。これは今回の接続確認の区切りであり、恒常的に2世代でしか動かせない仕組みにはしない。将来の実行単位も開始時に世代数・総局数を台帳へ固定し、残予算が不足する新工程は起動しない。予算終了時に既存の実行・保存・報告の責任を放棄しない。

ユーザーの停止指示は常に優先する。次工程を起動せず、対象の継続タスクを停止し、実行中の当該研究と保存状況を整理する。他目的のrunnerは停止しない。

## 実装が必要な残件と完了判定

既存の run_selfplay_value.py は選別→1000局確認→親更新→300局→再学習を1回完了したが、生成した次モデルを選別へ戻す制御や確認タスクへの接続を検証していない。

必要な実装は、工程別の再開入口、次モデルへのpreflight再適用、親と分割の世代間継承、残予算と停滞分岐、同一タスクの登録/更新receipt、重複照合と比較更新である。

接続の検証では、親更新あり/なしの両分岐、発火遅延、未完了からのETA更新、起動応答不明、保存失敗、同時再開、ユーザー停止をまず小さな実データで確認する。合成テストに通っただけで大量対局やタイマー接続成功と扱わない。実際の一回限りタスクの発火により、前工程の保存読み戻し→次工程の実開始→同一タスク更新がつながった記録を残す。予定工程まで終わったら全Releaseの読み戻し、2回の親判定、次回用原本/モデル、タスク停止を確認し、完了と未接続を分けて報告する。
