# v2.0.17を基盤とする強化候補の比較

2026-10-15〜16 JST。本人指示に従い、既存機能の再実装より先に、小さく切り分けられる差分評価・並列探索・自前自己対局学習を順に実装し検査した。正式採用版はKUMOJI v2.0.17のまま。候補は研究ブランチで管理し、既定値や正式比較基準へ昇格させていない。

| 候補 | 確認結果 | 採否の提案 |
|---|---|---|
| 駒得・効きの差分更新 | 計算結果は一致、速度改善は確認できず | 保留 |
| 2スレッド探索 | 固定深さの処理時間は改善、実戦104勝96敗（52.0%） | 棋力向上の根拠が不足、保留 |
| 自己対局MLPを25%混合 | 勝敗予測は改善したが、実戦35勝165敗（17.5%） | 今回の候補は不採用を提案 |

今回の候補から、正式版へ採用すべき強化は確認できなかった。正式な採否は本人判断とする。

## 比較条件

固定基準は正式v2.0.17 `003f42c66f8e3f2e5deb1898103555466e72016f`。実戦は200ms＋AdaptiveLongThink ON（条件により最大1秒、1局10回まで）、初手ランダムON、最大300手。同じ採用済み局面知識163件（SHA-256 `6da204cd1e65600ccdbb9f3dbe463627687d6cf7eb8347da6a103239129dac4c`）を両側へ渡した。採用済み探索設定23/8/6/4と評価配点を維持した。

並列候補は `3cd566957095325287f7043409a866fdbab9ef2e`、学習候補は重みと混合率を固定した `00904045c69c5c76ca78f85b5a47391bfb5c1a86`。build jobの実checkout SHAを読み戻した記録は `match-build-proofs.json`。設定だけでなく実体ハッシュ、知識hash、棋譜の再生を確認した。

## 差分評価

駒得・効き情報を部分更新する研究用 `EvalUpdateMask` を追加した。通常は0（無効）。ランダム合法局面2500件、任意局面切替、巻戻し、成り、持ち駒、玉を透過する射線を含め、攻撃マップ全項目と複数配点の評価内訳が従来計算と一致した。固定深さでは手・評価・PV・ノードまで一致した。

24局面×3反復の固定深さ2診断結果は次のとおり。倍率は正式版に対する処理速度（大きいほど速い）。

| 更新内容 | 各試行の速度倍率中央値 | 合計時間からの速度倍率 | 判断案 |
|---|---:|---:|---|
| 駒得だけ | 0.973 | 1.009 | 改善が安定せず保留 |
| 効きだけ | 0.934 | 0.956 | この実装では遅く、保留 |
| 両方 | 0.912 | 0.958 | この実装では遅く、保留 |

OFFの対照は中央値1.013、合計1.054倍だったため、数%の変動を改善とは見なさない。200ms診断でも深さの改善はなかった。これらは実戦比較へ進めなかった。差分更新そのものが将来役に立たないとの結論ではなく、この評価関数と更新方式での結果である。詳細は `incremental-measurements.json`。

## 2スレッド探索

rootの全合法候補を2本へ分担し、各探索の置換表・局面・評価キャッシュを分離した。同じ完了深さの結果だけを統合する。時間制御と長考は親側で管理し、node制限時は直列に戻す。研究用 `SearchThreads` の既定は1。

固定深さ2の72試行で評価点が全一致。手順や探索量は並列化により変わる。直列対照は手・評価・PV・ノードが全一致した。固定深さの合計時間は1.335倍の速度、中央値1.316倍。200msの深さ合計は193→196と小幅な改善にとどまった。2スレッド分のCPUを使用する結果であり、1スレッドの無償高速化ではない。詳細は `parallel-measurements.json`。

[200局比較 run 38732451498](https://github.com/mtk-ctrl/shogi-ai/actions/runs/38732451498) は **104勝0分96敗、勝率52.0%**。先手100局・後手100局、それぞれ52勝48敗だった。Wilson 95%区間は45.1〜58.8%、五分に対する両側二項検定p=0.621（対局独立を仮定）。同一の全着手列が4局分重複しており、区間は独立した多様な局面での保証ではない。現時点で棋力向上を断定せず、採用保留を提案する。

200局・21,954手をpython-shogiで再生し、全着手の合法性、全最終局面、200局の詰みを確認した。壁時計の最大応答は候補991.9ms／正式版991.3ms、1.1秒超は双方0手、長考は1局10回以内。知識ファイルは両側とも同一で読み込める条件だが、この対局群で知識一致は0回だった。照会は候補20,537回／正式版10,406回。深さ・ノードの実戦集計は異なる局面群での観測なので、速度比較へ転用しない。詳細は `parallel-match-audit.json` と `parallel-match-summary.json`。

## 自前自己対局の学習評価

同じ固定v2.0.17同士の[200局 run 38731311364](https://github.com/mtk-ctrl/shogi-ai/actions/runs/38731311364)から、重複3局を除いた197局・1576局面を使用した。実バイナリのhashはビルドパス等で異なるため「同一バイナリ」とは呼ばない。debug・build-id・診断パスだけを正規化した実行コードの一致、同じ実checkout、同じ設定・知識を確認した。

局単位で学習157局、検証18局、テスト20局へ分け、検証・テストから既出の同一盤面・持ち駒・手番を除いた。検証集合だけで中間層16素子・4epoch・NN25%＋従来評価75%を選び、その後に重みと混合率を固定した。これは独自の小さなMLPであり、NNUEやAlphaZero型強化学習の完成実装ではない。終局・詰み判定は置き換えない。

未使用テスト128局面の勝敗予測Brier誤差（小さいほど良い）は、従来評価0.22722→混合0.20951。局単位bootstrapによる誤差改善95%区間は0.00017〜0.03695。ただし独立テストは20局と小さく、予測誤差の改善を棋力向上とは扱わない。後から加えた診断では、学習集合の先手勝敗傾向だけを使う定数予測のテスト誤差は0.25605だった。この追加診断でモデルの選び直しはしていない。

重みのPython/C++照合は1576局面で最大確率差8.99e-8未満。実際のActions対局バイナリでも `EvalNeuralBlend=25` が反映されることを確認した（`neural-runtime-probe.json`）。既定は0。学習手順・出所・モデルhashは `learn_selfplay.py`、`selfplay-learning-report.json`、追加診断は `learning-prior-diagnostic.json` に残した。

[独立した200局比較 run 38804852520](https://github.com/mtk-ctrl/shogi-ai/actions/runs/38804852520) は **35勝0分165敗、勝率17.5%**。先手23勝77敗、後手12勝88敗、Wilson 95%区間12.9〜23.4%だった。今回は大きな弱化であり、この重み・混合率を採用しないことを提案する。結果を見た混合率の調整や追加モデルの選び直しは行っていない。

200局・19,801手を独立再生し、全着手の合法性、全最終局面、200局の詰みを確認した。全着手列の重複は2局分。候補の最大応答991.4ms／正式版991.5ms、1.1秒超は双方0手、長考は1局10回以内だった。知識照会9,139回／8,865回、一致0回、双方同じ知識hashである。追加確認したバイナリのhashもmanifestと一致した。詳細は `neural-match-audit.json`、`neural-match-summary.json`。

候補の記録された平均完了深さは3.38、正式版は3.07だったが、実戦では大きく負けた。異なる局面群の深さは制御された性能比較ではなく、深く読めたことだけで強化とは判断できない。弱化の主因は未特定であり、データ量だけが原因とは断定しない。少数の自前棋譜から得た勝敗予測器を、そのまま探索評価へ混ぜる方法は、今回の実戦検証に耐えなかった。

## 検査・保存・次の候補

追加した差分評価・並列探索のテスト、USI回帰（2スレッド設定を含む）、独立した合法性検査を通過した。ASan/UBSanも通過したが、ホスト環境の制約でLeakSanitizerは無効にしており、メモリリーク検査を通過したとの主張はしない。既存Quick CIも候補commitごとに成功（38731901589、38733198264）。研究データにPV・未着手候補を新たな長期蓄積として追加していない。

着手原本は標準の圧縮artifactを読み戻した。並列比較は2027-01-13 12:08:53 UTC、学習評価比較は2027-01-13 20:48:01 UTCまでの期限付き保存であり、Releasesへの長期移送完了とは扱わない。コード・小さな集計・監査手順はこの研究ブランチに保存した。

提案されたαβ探索、静止探索、置換表、合法手生成のビットボードは既に存在する。今回は重複実装を避けた。次の候補は、この結果を踏まえた評価学習のデータ拡充・対称性や外挿の検査、または並列探索の余分な探索を減らす方式である。MCTS・GPU・大規模NNUEは別の探索・学習設計と計算資源を要するため、小さな変更の延長として同時に混ぜる段階ではない。
