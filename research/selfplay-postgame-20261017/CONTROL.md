# 自己対局の改善循環と確認タイマー

2026-10-17 JST。[融合設計](DESIGN.md) と [報酬設計](REWARD.md) をつなぐ、今回の研究用進行設計。本人の「循環が回るようにタイマーも合わせて設計してください」と「続きをお願いします」に基づく。正式採用はR10の本人判断とし、研究世代の更新と区別する。

## 一世代の試運転

保存済み自己対局から開始し、再分析→原因別候補→比較→保存・報告まで接続する。厳しい進行条件を通った場合だけ、その研究候補同士で次回用100局を作り、原本・合法性・保存・再取得hashまで確認する。この100局からの次の最適化は自動追加しない。

不合格なら親世代を保持し、何が改善できなかったかと次の仮説を保存する。正式Engine・版番号・既定値・採用済み163件の知識・正式比較基準は変更しない。無期限の大量対局を始める設計ではない。

数値はAIが事前固定する今回の実験条件であり、恒常Ruleや本人が決めた正式採用基準ではない。新規対局前に、実装できた候補・コードSHA・入力hash・学習係数・分割・種・検査条件を研究branchのPLANへ凍結する。結果を見て候補追加・再調整・確認のやり直しをしない。

## 状態と完了証拠

| 状態 | 処理と次へ進む条件 |
|---|---|
| 準備 | 最新main/他チャットと照合。固定親・研究branch・実装PLANを作成し、共通reader/再分析/生成器を実装・検査 |
| 原本確認 | 保存済み自己対局を復元し、全実戦手・終局・実バイナリ・設定・知識・hashを照合 |
| 再分析 | 両側・問題手/好手候補/静かな対照を、固定自作Analyzerで完全な実戦履歴付き再分析 |
| 原因分け | 評価・探索・局面知識・保留へ振分け。比較不能や不明例を無理に学習へ入れない |
| 候補固定 | モデル/パラメータ/候補知識のhash、コードSHA、条件と分割を凍結 |
| 軽量検証 | 合法性・符号・駒取り・反復・欠損・知識利用・補正上限・速度を検査 |
| 選別 | 最大3条件各100局。実適用設定・全実戦手・終局を監査し保存 |
| 確認 | 選別最良が50%以上なら未使用seed200局を一度だけ実行。候補は再調整しない |
| 次回用原本 | 進行条件を通った研究候補同士100局を生成し、合法性と保存hashを検証 |
| 完了 | 成果物読み戻し・CI・保存receipt・結果と限界を報告後、確認タスクを停止 |

run_id / attempt / 実開始 / 最終結果 / 入出力hash / 検査 / Release receipt を別々に保存する。起動入口成功は本体開始や保存完了ではない。state.jsonは進行台帳であり、単に値を更新して実行成功と扱わない。現在の実測と進行はstate.jsonとRESULTSを参照する。再分析・K1生成・軽量検査・100/200局比較・全手監査・保存/判定を一世代分検証した。AIと明示依頼で進める経路であり、対比較学習器と多世代の無人制御は未実装。今回の評価学習は適格例不足で見送った。

## 予算と研究上の進行条件

- 初回入力は第2回の保存済み500局（38946175603 / 38946985753 / 38947702135 / 38948701892）。元1000局を含め、既使用データを新しい独立testとは呼ばない。Release/hashは第2回publicationで照合する。
- 研究は最大96選別局面、同一局最大4局面。両手番・各段階・問題手/好手候補/静かな対照を対象とし、分布と不足を報告する。50/500msを基本に、重要例だけ最大5秒。追加回数の上限は実装PLANに固定する。
- 符号、cp/mate、完了深さ、境界、反復を検査。長い再分析でも正解証明としない。不安定・強制悪化・欠損は保留する。
- 調整/選択/未使用診断を局・近似局面の重複群で分ける。成立する分割がなければ不足を結果とし、同じ例で訓練と性能主張をしない。
- 候補は評価補正、追加の候補知識、その併用の最大3条件。探索原因は再発問題と次の仮説へ送る。学習可能な根拠が不足なら学習を強行しない。
- 新規対局は選別最大300＋確認200＋通過時の次回用100＝最大600局。候補が少ない/不合格なら減る。新しい1000局や追加候補探索は含めない。
- 比較Bは準備時の正式main Engineの固定SHA。双方R20の200ms＋条件付き長考、同じ採用済み知識、現行探索設定。追加の候補知識だけAへ別snapshotとして渡し、正式知識を上書きしない。並行の正式更新があってもBを無断交換しない。
- 同一runner内で、無効化時の固定深さ一致と既存方式の速度診断。200ms深さ合計が基準の90%以上を最低条件とし、対象・反復・設定をPLANへ記録する。
- 選別同点は小さい変更を優先。確認から次回用原本生成へ進めるのは、200局の得点率の概算95%下限が50%を超え、全監査・保存・回帰を通った場合だけ。得点率は引分0.5。区間は p ± 1.96×sqrt(p×(1-p)/n) を0～1へ制限する事前固定の概算とする。引分を含む点数への保守的な分散近似であり厳密二項区間とは呼ばない。
- 完全棋譜重複・学習元/選別との一致・先後の感度を開示。重複除外でも下限50%超が崩れた場合は次世代へ進めず保留する。反復対局の相関をこの区間で完全に補正できたとは言わない。
- 条件を通っても研究候補のまま。条件不成立は親を保持した正常な研究結果として報告する。96局面や200局であらゆる棋力差が分かるとは主張しない。

## 一つの確認タスク

一つの循環IDに有効な確認タスク一つを対応させる。終了済み第2回タスクは再開しない。各段階で別タスクを作らない。今回だけ、登録種別の変更機能がないため旧反復登録を無効にし、一回限りの登録へIDを引き継いだ。対応はstate.jsonに保存する。研究自体は継続する。

本人の2026-10-17の訂正に従い、毎時の反復を終了し、工程の終了見込み時刻へ一回限りの確認を設定する。実開始は可能なら同じ作業ターン内に直接確認する。対局開始後は同種実測・残局数・最後のshard・build/queue/集約/保存時間からETAを計算し、同じ一回限りタスクの時刻を更新する。未完了なら実進捗を読み直して新ETAへ更新する。固定間隔のポーリングや反復制限を回避する短時間連続実行にはしない。提供機能の実際の制約にはR21に従う。

毎回ルーター→必要active Ruleを最初に読み、最新main/研究branch/state/既存run/他目的runnerを取得する。同目的のrunがあれば追跡し二重起動しない。完了なら成果物検査と保存後に次段階へ進む。一回の発火で短い複数段階を進めてよい。実行中は進捗/ETA/見積根拠/次工程をstateへ記録し同じ一回限りタスクを更新する。対局未開始なら準備・起動確認の見込みであることを明記する。

失敗時は対象Ruleと原因を調べ、許可された修正・再検査を行う。安全性拒否を別経路で迂回しない。監査だけの修正で原対局をやり直さない。完了は結果と限界を報告してから同じタスクを停止する。継続不能なら具体的障害と未完了項目を報告する。

起動ごとに実空きrunnerを取得し全空きへ均等配分する。他目的の有効runは止めず、R21の1job=1laneを維持する。

## 中断・重複への制御要件

以下は実装時の必須条件。設計保存だけで実装済みにしない。

1. 操作キーを循環ID/世代/段階/固定入力hashで作り、起動前に意図を台帳へ保存。応答不明時は既存要求/runを照合してから判断する。
2. state更新は期待branch headとの比較更新。競合時は最新を読み直し、他チャットの変更を保つ。
3. 複数起動元の処理は同じconcurrency groupで直列化しcancel-in-progress=false。タイマーとActionsで起動責任を二重化しない。
4. バイナリ・モデル・知識を凍結し、対局中に学習結果へ差し替えない。pending要求を上書きして他の依頼を失わない。
5. 保存はReleaseのasset/hash/bytes読み戻しで確定。同名異hashは上書きしない。通常の全未着手候補/PV/探索木は長期保存へ広げない。
6. 欠損・保存不能は後続を止め成功扱いしない。使用済みtestを未使用へ戻さない。
