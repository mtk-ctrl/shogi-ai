# 対局ランナー・終了予定・報告タイマー運用基準

## 目的

目的はrunner数を増やすことではなく、**指定された全対局を最短時間で完了すること**である。

そのため、対局開始時に現在のGitHub Actions実行状況を確認し、空いているrunner数に合わせて総対局をできるだけ均等に分割し、原則1巡で完了させる。
あわせて終了予定時刻を算出し、その時刻に結果確認タイマーを設定する。

## 1. 対局開始時のrunner配分

開始直前に、実行中・queuedのGitHub Actionsを確認する。

既知の同時実行上限から、停止してはいけない有効なrunが占有しているrunner数を引き、**その時点で実際に使えるrunner数**を決める。

その後、全対局をそのrunner数へできるだけ均等に割り当てる。

原則:

- 20 runner空いているなら、20 jobで全局を1巡に割り切る。
- 17 runner空いているなら、原則17 jobで全局を1巡に割り切る。
- 空きrunner数より多いjobを作り、意図的に2巡目の待機jobを発生させない。
- 空きrunner数より少ないjobしか作らず、runnerを遊ばせない。
- 1 runner内で複数CPUレーンを同時実行してrunner数不足をごまかさない。原則1 Actions job = 1対局laneとする。
- 各jobの想定所要時間ができるだけ揃うよう、局数だけでなく相手の探索量等も考慮して割り当てる。
- 先後数は全条件で均衡させる。Shardごとの局数は可能な限り偶数にする。
- Experience Cacheを使う場合、各laneは独立したExperienceFileを持ち、そのlane内では対局をまたいで継続利用・保存する。

### 例

600局、20 runnerが空いている場合、目標は約30局/runnerである。
条件ごとに完全な30局分割ができない場合も、24 jobを作って4 jobを2巡目へ送るのではなく、**合計20 jobの範囲で32～34局等に再配分して1巡完了を優先する**。

## 2. 実行中の他workflowを停止してよい条件

**runnerを空けるためだけに、別目的の有効なrunを停止してはいけない。**

停止してよいのは次の場合だけである。

1. 同じ目的のrunを、条件・Shard構成・実装を修正して再実行し、旧runの結果が不要になる場合。
2. 新しいcommit/runが同じ検証を完全に置き換え、旧runがobsoleteになった場合。
3. ユーザーが明示的に停止を指示した場合。

停止してはいけない例:

- 別テーマの有効な対局
- 意味のある夜間学習・自己対局
- 別条件の比較実験
- 必要なCIやAPK生成

これらは新しい対局のrunner確保だけを理由に停止しない。
新しい対局側が、残った空きrunner数に合わせて局数を再分割する。

## 3. 対局開始時に必ず報告する項目

workflow起動後、run IDを確認した同じターンで次を報告する。

- 総対局数
- 条件
- 開始時の同時実行上限
- 他の有効runが使用中のrunner数
- 今回利用するrunner数
- job/Shard数
- 1 jobあたりのおおよその局数
- Experience/Book等の主要条件
- workflow run ID
- 終了予定時刻

## 4. 終了予定時刻

終了予定は、直近の同種workflowの実測時間を優先して算出する。

見積りには以下を含める。

1. build
2. artifact受け渡し
3. queue
4. 対局
5. 集計・artifact upload

対局jobの最大所要時間を基準にし、平均ではなく**最後のrunnerが終わる時刻**を終了予定とする。

## 5. 結果確認タイマー

workflow run IDを確認したら、**同じターンで終了予定時刻にChatGPTの結果確認タイマーを必ず設定する**。

タイマー実行時:

- 完了済みなら、結果を集計して報告する。
- 未完了なら、進捗・残runner・新しい終了予定を確認する。
- 必要なら新しい終了予定時刻に再確認タイマーを設定する。
- ユーザーの指示なしに追加対局を開始しない。

## 6. 2026-10-07の失敗

Book+ExperienceのLv40/45/48/49/50/55再測定600局で、6レベルを6 Actions jobに固定し、各job内で4レーンを回した。
これは空きrunnerを使い切らず、最短完了という目的に反した。

その後「24 jobを投入して20 runnerを埋める」案も出したが、4 jobが2巡目へ待機するため同じく不適切である。

正解は、開始時の空きrunner数に総局数を再配分し、**可能な限り全runnerがほぼ同時に終わる1巡構成**を作ることである。
