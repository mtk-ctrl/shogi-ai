# ルール層の分離設計と検証

## できるようになったこと

やねうら王の局面管理・合法手生成を利用し、その上に自作戦略を接続できる。
v0.0.2の戦略は合法手から1手をランダムに選ぶだけであり、駒の価値・先読み・学習はまだ実装していない。
不成、二歩、打ち歩詰め、王手、千日手の判定もやねうら王の実装を利用する。

| 場所 | 役割 | 今後の変更方針 |
|---|---|---|
| `engine/main.cpp` | USIの局面受信と指し手送信 | 通信機能を追加するときに変更 |
| `engine/rules/position.h` | 自作側に公開するルールの窓口 | 戦略に必要な情報が増えたら拡張 |
| `engine/rules/position.cpp` | 窓口とやねうら王を接続 | ルールを独自に再実装しない |
| `engine/strategy/random.h` | 今回の仮の指し手選択 | 評価・探索を開発する場所 |
| `third_party/yaneuraou/` | 原典の固定情報と分離差分 | 上流更新時だけ検証して更新 |

## 原典と切り離し方

原典は [yaneurao/YaneuraOu](https://github.com/yaneurao/YaneuraOu) のコミット
`c1b80eaa09fe13d5f12b1599d1ae4d53c224de30`（2026-09-14、9.80git）に固定する。
ビルド時にその版を取得し、必要ファイルごとにSHA-256を照合する。最新版への自動追従はしない。

取り込むC++実装は `position.cpp`、`movegen.cpp`、`bitboard.cpp`、`types.cpp` の4つ。
`USER_ENGINE` の設定を利用し、評価関数・探索・SEE・手の並べ替え・詰め探索を有効にしない。
標準のUSER_ENGINEサンプルやエンジン全体を組み込む方式ではない。

上流との差分は `rules-only.patch` に残す。変更は条件付きコンパイルで、次の依存を外すものである。

- エンジン全体に依存する上流テストコマンド
- 置換表を先読みするためだけのテンプレート実体化
- 探索用のnull move（実際の対局のパスではない）
- 探索用の引き分け評価値テーブル
- 上流USIエンジン全体への文字列変換の依存

指し手文字列の出力は、上流 `usi.cpp` の該当処理を小さな補助ファイルに移した。
合法手生成、指す・戻す、打ち歩詰め、千日手、入玉の判定本体は書き換えていない。
上流ヘッダーには評価用の宣言や無効な条件分岐も残るが、実行ファイルに評価・探索の処理は含まれない。
`tests/check_boundary.py` で入力ソース一覧と実行ファイルのシンボルを検査する。
リンク時の未解決参照の無視や不要コード除去で依存を隠す方法は使用していない。

## 壊れやすい箇所への対応

### 不成も含む合法手

`LEGAL_ALL` を呼び出す。不成の一部を省く通常探索用 `LEGAL` との差である。
不成のルールは上流からそのまま借りる。

### 千日手

`ENABLE_QUICK_DRAW` は有効にしない。上流の正規判定を呼び、`is_repetition(0)` によって
探索中の早期打切り用の繰り返しと、実際の4回出現を区別する。
遡り範囲は上流既定の16手から全履歴に広げる。
優等・劣等局面という探索上の結果を、対局の勝敗に変換しない。

局面履歴の `StateInfo` は `deque` に置き、手数が増えてもアドレスが変わらないようにする。
`undo()` は戻してから履歴を取り除く。`clone()` は初期局面と全着手を再現して千日手履歴を保つ。
SFENだけをコピーすると過去の繰り返しを失うため、代用しない。

### 入力と終局

SFENは盤面の大きさ・駒数・玉の数・持ち駒の表記・手数の範囲を先に検査し、上流パーサーへ渡す。
手は合法手一覧と照合する。不正な入力があっても直前の正しい局面は保持する。
USI側では入力失敗を記録し、その後の `go` で古い局面の手を返さない。

ルールAPIの `status()` は詰み・合法手なし・千日手・連続王手の勝敗を返す。
`play()` は終局後の着手を拒否する。`legal_moves()` は終局後も盤上の幾何学的な合法手を返す仕様で、
対局を進めるかは必ず `status()` で判断する。

入玉はCSA27点法の宣言条件を提供する。宣言は自動終局ではない。
持ち時間、合意による持将棋、最大手数、投了の管理は対局側の仕事である。
トライルールや独自の持将棋規定は今回の公開APIには含めない。
通常対局向けとして、初期SFENには双方の玉を要求する。片玉の詰将棋は対象外。
任意SFENの全てが初期局面から到達可能であることまでは検証しない。

### USIとGUIの責任

USIには千日手の引分け・連続王手による勝利を返す専用の `bestmove` がない。
本エンジンは判定結果を `info string terminal ...` で知らせる。
GUIが終局後も `go` を送った場合は盤上の合法手を返し、引分けを投了に変換しない。
最終的な勝敗表示と対局停止はShogiDroid2側で行う。
実機での千日手の表示連携は未確認であり、ルールAPIの検証済み範囲と区別する。

`go ponder` と `go infinite` は指し手を保留し、`ponderhit` または `stop` で1回だけ返す。
`go mate` はv0.0.16以降の自作詰み探索で扱う。v0.0.18で最大7手へ拡張し、v0.0.19では時間制限付き通常`go`に1～3手のMateAssistを組み込んだ。時間管理はv0.0.14で自作実装済みである。

## 再現手順

```bash
python3 -m pip install python-shogi==1.1.1
python3 scripts/build.py
python3 scripts/build.py --test --output build/rules-test
./build/rules-test
python3 tests/differential.py build/rules-test
python3 tests/test_usi.py build/shogi-ai
python3 tests/check_boundary.py build/shogi-ai
python3 scripts/build.py --test --sanitize --output build/rules-sanitized
./build/rules-sanitized
```

必要なのはGit、Python 3、C++17コンパイラ。`python-shogi` は照合用テストだけの依存で、APKには含めない。
Androidは同じビルドスクリプトにNDKのコンパイラと `--android` を渡す。
GitHub Actionsが検証を通過した後にAPKを生成する。

## v0.0.2時点の次の戦略開発（履歴）

`Random::choose()` を入口に、まず自作の駒得評価を追加できる。
盤面と持ち駒は `snapshot()`、候補手は `legal_moves()`、先読みは `play()` と `undo()` を使う。
やねうら王の評価値・駒価値・探索を呼ぶ必要はない。
今回のランダム戦略は接続確認用であり、棋力向上の成果とは扱わない。

## v0.0.3での利用

分離済みのAPIをそのまま使い、`engine/strategy/material.h` に自作駒得評価を追加した。
ルール層・上流パッチ・上流固定版は変更していない。旧 `random.h` は比較・学習用に残す。
