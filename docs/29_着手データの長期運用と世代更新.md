# 着手データの長期運用と世代更新

## 位置付け
2026-10-07のオーナー指示「対局量は最大で毎晩1万局程度として調整する。1か月・半年と蓄積が増え、雲路も強くなる前提で設計する」に基づく長期運用仕様。
保存範囲の正本は `docs/rules/R25_着手記録の保存.md`、各記録の項目は `docs/28_着手記録の保存仕様.md`。
保存・検索基盤について本書の設計を採用する。概念構成は「対局記録・研究記録・局面知識」で本人承認済み。保存と即活用の接続仕様はdocs/35。知識の正式採用・直接着手・自動更新は、R10・R25に従い別途検証して決める。
新しい収集・長期移送・索引・対局用データ生成は未実装。毎晩1万局は容量計画の上側の想定であり、最低局数・起動指示・自動対局の設定ではない。

## 増えていくものと小さく保つもの
| 層 | 保持するもの | 長期運用 |
|---|---|---|
| 実戦・研究の原記録 | 全実戦手、当時の評価と条件、別途行った研究と出所 | 追記して蓄積。古い版の結果も消さず、後日の研究で上書きしない |
| 共通設定・知識資産 | エンジン設定、局面知識の版・内容ハッシュ・必要な実体 | 内容hashで共有。同じ資産を局数に比例して複製しない |
| 検索索引 | 局面から該当記録への参照、版・日時・条件・出現数 | 増分生成。分割し、研究対象に必要な範囲だけ取得 |
| 対局用の知識候補 | 今のエンジン向けに確認した実戦手・研究手と適用条件 | 原記録から選んだ別の派生資産。容量・メモリ予算内に収める |
| 診断用Raw・作業キャッシュ | 調査・転送に使う一時ファイル | 長期正本と区別。原記録の転送を確認する前に保存期間を短くしない |

半年分の原記録を毎局の開始時に全件読み込む構成にしない。対局中にReleasesを検索・ダウンロード・展開しない。
対局用データは開始前に取得・hash検査・読込みを済ませ、探索時間内ではローカルの小さな索引だけを使う構成を目指す。
原記録の保持量と対局用データの大きさを連動させない。対局用データから外した局面も原記録には残り、再研究できる。

## 保存単位と移送
### 月別の入れ物、run別の確定記録
- Releasesのデータ用releaseをJSTの月ごとにまとめる。例: `records-2026-10-01`。末尾は同月内の保存区分番号で、製品Engine版ではない。月は対局開始時刻で決め、実データの日時はUTCで記録する。
- 確定する実体はrun/attempt/partごとの圧縮ファイルとmanifest。月全体を毎晩再圧縮・再アップロードしない。1runが大きければ256MiBを超える前にpartへ分割する。
- 通常はshard結果を対局後のaggregateへ集め、共通の保存処理から送る。shardごとに大量の小さなrelease・資産コピーを作らない。大規模runではpartごとの処理を許容し、manifestでshardとの対応を保持する。
- 月末を待たず、各runの完了・回収後に長期移送を確認する。月別整理を理由にartifactの期限まで放置しない。
- 各releaseのasset数を数え、追加すると800件を超える場合は同月の次区分へ送る。確定前のmanifest・索引等も件数に含める。これは公表上限1000件までの余裕を残す運用目安である。
- タグはその保存区分を作った収集コードの確定commitを指す。各runの収集コード・schema・エンジンcommitはmanifestで個別に識別する。
- データreleaseを製品のlatestにしない。Androidの配布処理が製品releaseのみを選ぶことも実装時に確認する。

GitHubの公表条件は1asset 2GiB未満、1release 1000assetsまで。分割して保持し、総量を無条件に放置しない。
根拠: https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases

### 追記、重複、途中失敗
確定ファイルは上書きしない。同名・同hashの再送は既存実体を取得し直して確認し、同名・異hashなら失敗として報告する。
違うrunで実際に指された同じ棋譜は別の観測なので、棋譜内容が同じというだけで削除しない。転送の再実行と新しい対局を、run/attempt/game IDで区別する。
同じ対局の再処理は出所IDで重複を検出する。異なる出所に見える旧データで対応が断定できない場合は、疑いを記録し、自動削除しない。
途中で落ちたrunは完了局チェックポイントを回収し、完了・中断・不明を区別する。部分回収を全局保存成功と表示しない。

manifestの状態は生成・検査済み、移送済み、取得hash確認済み、索引済みを区別する。アップロードだけで長期保存成功にしない。
保存一覧は取得hash確認済みのmanifestから再生成できる。索引処理の失敗は記録の移送成功と分けて報告し、再開時には未処理分だけを扱う。
複数runの保存が並行しても、全体一覧の上書きで一方を消さない。run manifestは独立保存し、一覧は入力manifestの集合ハッシュと世代を付けた時点版として生成する。
共通資産の作成はhash単位で直列化するか競合を照合する。同じhashを別名で物理的に重複保存した量も台帳へ出す。
古いschemaを消す全面書換えや、旧実体を残したままの全履歴再コピーは通常運用にしない。reader側で互換性を持たせる。

## 全履歴を読まない検索
### 索引のキーと出所
盤面検索キーは、駒の配置・双方の持駒・手番とルール識別子から作る。SFENの手数欄だけが違う同一盤面を別局面にしない。
hashだけで一致を断定せず、対象を取り出した時に盤面内容を照合する。
盤面キーと到達履歴は分ける。同じ盤面の研究資料をまとめて探す一方、千日手・連続王手・到達手順等の影響を含む完全な履歴は元の開始SFEN＋実戦手順から確認する。
到達履歴のdigestは候補の絞り込みであり、ダイジェスト一致だけで検索の打切りや評価再利用を認めない。

索引の値は対局ID・直前の手数・元のpart hash・エンジン設定ID・解析条件・品質状態等への参照とする。
棋譜や評価の全内容を索引へ二重コピーしない。gzipファイル内の行番号は展開後の参照であり、圧縮バイト位置として扱わない。

### 増分作成と更新
- 新たに確認済みとなったpartだけを順に読み、局面を復元して索引の差分を生成する。全対局をメモリへ載せず、逐次処理する。
- 盤面キーのhash範囲で索引を分割する。研究対象のhash範囲に対応する索引と、該当する元partだけを取得する。
- 特定のhash範囲が大きくなったら、その範囲を再分割する。分割対応表も元manifest集合と版を持ち、全履歴の巨大索引を毎回取得する構成を避ける。
- 分割数・索引1件のbytes・展開メモリ・検索時間は実装後に測る。索引の容量を「棋譜より小さい」と前提にしない。
- 新しい差分が増えたら対局後に同じ範囲をまとめる。まとめた索引の内容・件数・入力集合hashを照合し、読込み側の参照を新世代へ切り替える。
- 検証する最新索引の重ね読みは基底1個＋差分最大7個を初期目安とする。超過時は該当範囲だけ再構成する。読み取り中の時点版を途中で置き換えない。
- 旧索引を残し続ける量、再構成中の新旧二重領域、一時展開bytesも容量台帳へ計上する。原記録と異なり再生成可能だが、既存実体の削除は勝手に行わない。
- 索引を全損しても、保存確認済みmanifestと原記録から再生成できることを完了条件にする。

出現回数・再研究済み件数・異なる条件での観測数は別に集計する。同じ設定・近いseedによる反復自己対局を、独立した多数の根拠と誤認しない。

## 雲路が更新されたときの扱い
Engine世代名だけでなく確定commit・実体hash・有効設定で区別する。新しくなればすべての局面で旧版より正しいとは限らない。
当時の評価と深さはその版の観測である。旧版のdepth 20と新版のdepth 18を数字だけで優劣判定しない。探索や評価関数が変われば深さ・cpの意味も変わり得る。

| 種類 | 新版での扱い |
|---|---|
| 過去の原観測 | そのまま保存し、新版の結果を追加して比較する |
| 旧版で選ばれた深い手 | 新版研究の候補・探索順序の検証材料として取り出す |
| 旧版の点数・境界値 | 新版の置換表へ確定評価として投入せず、探索打切りの根拠にしない |
| 新版で再確認した手 | 確認した対象commit・条件・日時・根拠を付けて知識候補へ入れる |
| 新旧で割れた手・不明な条件 | 確認待ち・相違ありを明示し、旧観測を消さず再研究へ回す |
| 古い版でしか現れていない局面 | 年齢だけで捨てず、頻度・重要性に応じて新版で取り出す |

知識候補に `unverified/confirmed/disputed/inapplicable` 等の確認状態と対象エンジン条件を付ける。欠損・曖昧な旧評価をゼロや確定値に変換して候補の採用根拠にしない。手の利用時にも現在の局面の合法手と照合する。確認は条件に結び付くもので、永続的な「正解」ラベルではない。
新版の評価・探索・ルール・知識依存が変わった場合、既存のconfirmedを無条件に継承しない。候補版を分け、必要な範囲を再確認する。
旧版の観測を記録上の着手から消すことと、対局用データへ採用しないことを区別する。

## 研究時間を増加量に比例させない
毎晩の全局面を長考で読み直すと、棋譜の保存以上にCPU時間が増える。再研究は対象数とCPU時間の予算を設け、キューで優先順位を付ける設計にする。
優先する候補は、よく再登場する局面、新旧版で手が変わる局面、200msと長考で手が割れる局面、勝敗に影響した疑いがある着手、不安定・欠損・曖昧な観測、自前定跡の境界である。
頻出だけに偏らず、出現が少ない局面・中終盤も一定の研究枠へ入れる。その配分と長考時間は研究開始前に条件として決める。
同じ局面・履歴・Analyzer条件・解析制限の研究は共有し、元となる複数局から参照する。実際にもう一度解析した場合は新しい観測として記録する。
Analyzerが更新された場合や前回が不安定だった場合は、既解析であることだけで永久に再研究対象外にしない。

通常の実戦記録や未確認の研究手は、200ms探索の順序へ使う案を検証する。
1時間等の長考研究を単なる候補提示以上に使う案は `docs/30_長考研究結果の着手への利用案.md`。研究の時間・深さ・条件を渡し、確認済み研究手を既定の着手へ置く方式も別に比較する。採用条件・実装・強化効果は未確定である。
時間を長くした結果も正しさは保証されない。候補を確認する材料にし、直接着手・評価再利用・探索省略は別に検証する。
序盤で確認が進んだ連続手順と相手の実戦応手を組み合わせ、自前定跡の研究候補へ育てる。単独の中終盤研究は研究局面集として保持する。
原記録は局面知識の候補へ統合して扱う。局面知識の自動更新・正式採用・直接利用の具体的条件は、R10・R25に従い別途決める。

## 対局用データの予算と採用検証
原記録は全局保持する一方、対局用の知識候補は再確認の有無、利用頻度、観測の安定性、期待する効果、1件のbytesで選ぶ。
古い資料しかない手も研究候補には残す。頻度や深さの数字だけで無条件採用しない。
初回試作では知識用の追加常駐メモリ64MiB以内を検証目安とし、ロード時間・探索時の参照時間・利用率・棋力を測って調整する。ファイルの圧縮bytesとは別であり、エンジン全体のメモリ上限を意味しない。Android等への採用は別の実機確認を要する。
予算を越えた知識は対局用の候補から絞る。全原記録の削除や収集停止で調整しない。

比較する知識版は固定し、エンジン・知識ファイル・索引・選択条件のhashと出所manifestの集合を登録する。
研究に使った局面と検証用局面を区別し、学習元の同じ対局だけで効果を主張しない。固定した回帰局面に加え、作成後の対局等も用いる。
R20の正式条件で同じエンジンの知識あり・なしを比較し、先後を均衡させ、勝敗・不確実性・違法手・総時間・探索量を確認する。
参照時間を200msの外へ隠して評価しない。プロセス開始時のロード時間は別計測し、局数増加に伴う劣化も確認する。
新しいエンジンと新しい知識を同時に混ぜて効果を帰属しない。まずエンジン更新を比較し、その固定版で知識の差を確認する。
更新失敗・hash不一致・不適用な版は、利用対象から外して現行の確認済み版を維持する。原記録と失敗理由は残す。
比較と採用判断を通さず、蓄積したという理由だけでエンジンや知識を自動main反映しない。

## 1か月・半年・1年の容量計画
毎晩1万局を続けた場合の上側のシナリオ。MB/GBは10進、KiB/MiB/GiBは2進。局数を調整すれば通常記録の量は概ね比例するが、局の長さ・項目欠損・圧縮率も影響する。

| 期間 | 局数 | 計画6KiB/局 | 旧200局の核だけの試作を外挿 |
|---|---:|---:|---:|
| 1晩 | 1万局 | 61.44MB | 約22.25MB |
| 30日 | 30万局 | 約1.84GB | 約0.667GB |
| 180日 | 180万局 | 約11.06GB | 約4.00GB |
| 365日 | 365万局 | 約22.43GB | 約8.12GB |

試作2,224.85 bytes/局は追加項目をすべて含むschema 2の完成サイズではない。左の計画値も固定上限ではない。
研究記録、資産、索引、対局用の知識、一時Raw、転送中の二重領域はこの表に含まれない。全部込みの容量として表示しない。
半年で通常記録が数GB〜十数GBになり得ることを初期から想定し、月別の移送・分割取得を採用する。将来の保存先変更に備え、manifestはURLに依存しないID・hashを持ち、取得先は別の対応表から解決できるようにする。
移行時も元データhash、全実戦手、原評価、出所、研究参照が一致することを確認する。URLが変わっただけで記録を別の対局として増やさない。

### 確認頻度と通知
対局後にbytes内訳・局数・手数・平均bytes/局とbytes/手を記録する。入力数が多くても完全な保存一覧を毎回書き直さず、新規manifestの差分を追加する。
容量は毎月まとめて確認し、直近実測のペースと最大1万局/晩のシナリオについて30日・180日・365日の予測を出す。知識・索引等の増加は通常棋譜と別に予測する。
R25の1GiBは初回の容量点検地点とする。超過後に同じ通知を毎run繰り返さない。点検済みbytes・理由・対策・次回地点を台帳へ残す。
その後の累計点検地点は5GiB、10GiB、以後倍増を初期値にする。通常運用の停止・削除閾値ではなく、新たな容量段階を確認する目安である。
一時artifact100MiB、平均6KiB/局は同じ未解決状態をまとめて通知し、急増・新しい原因・対策後の再発は改めて報告する。
移送失敗、期限までに未移送、hash不一致、読み出せない資産、欠損増加は容量超過とは別に扱い、月次確認を待たず報告する。
既存データは自動削除しない。一時保存期間の変更は長期移送の実働確認後に別途行い、今回の設計だけで現行設定を書き換えない。

## 実装順と完了条件
1. docs/28のschema 2・不足項目収集・完了局チェックポイントを実装し、原記録の一致と欠損扱いを確認する。
2. 月別releaseへのrun/part移送、取得hash確認、資産の重複防止、増分台帳を接続する。期限付きartifactだけを長期保存と扱わない。
3. 逐次局面復元と分割索引を実装し、同一盤面・別履歴・再送・途中終了・並行保存で参照が混ざらないことを検証する。
4. 世代ごとの研究キューと知識候補を試作する。docs/35の構成・move_order_hint仕様を使い、正式採用・直接利用の未決条件を試作と混同しない。
5. データ量を10倍・100倍にした検証用入力と、最大想定の半年180万局相当（手数は実測分布）の入力で、最大メモリ、増分処理時間、必要partの取得量、索引再構成中のピーク容量を測る。実データの代表局でも確認する。
6. 全履歴を毎回読まないこと、64MiBの試作目安、200ms内の参照負担、版更新時の再確認、旧知識へ戻す経路を確認する。
7. 固定版での比較・採用判断を通し、結果と限界を記録する。長期運用の強化効果を保証したと報告しない。

本書の保存・長期運用設計は確定。性能計測、索引・研究キュー・対局用知識の実装、実際の強化効果は未確認である。
