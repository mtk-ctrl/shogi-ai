# 対局ランナー・終了予定・報告タイマー運用基準

## 目的

GitHub Actionsで対局を開始するとき、空いているhosted runnerを可能な限り使い、対局時間を無駄に延ばさない。
同時に、開始時点で終了見込みと結果確認時刻を明示し、完了確認を忘れない。

## 1. ランナー利用の原則

対局jobを「レベル数」「候補数」だけで分けてはいけない。
各条件の対局を複数の独立Shard/Laneへ分割し、**現在利用可能なrunner数を十分に上回る数のjobを投入する**。

原則:

- GitHub Actionsのmatrixに十分なShard/Lane jobを作る。
- 通常は `max-parallel` を設定しない。GitHubスケジューラ自身に、その時点で空いているrunnerを最大限割り当てさせる。
- 既知の同時実行上限よりjob数が少なくならないようにする。
- 他workflowがrunnerを使用中でも対局jobを減らさない。空き枠は即時実行し、残りはqueueさせる。
- runner数を節約する目的で、1 runner内に多数の対局laneを詰め込まない。CPU競合が必要な実験を除き、**1 lane = 1 Actions job** を基本とする。
- 対局条件・先後バランス・seed・Experienceの分離をShard化によって壊さない。

例: 6条件×100局で、各条件を4 lane×25局に分ける場合は24 jobを投入する。20枠が空いていれば20 jobが同時に走り、残り4 jobは自動で待機する。

### Experienceを使う対局

Experience Cacheを使う場合は、各laneに独立したExperienceFileを持たせ、そのlane内では複数局を通じて継続保存する。
並列化のために毎局Experienceを初期化してはならない。

## 2. 対局開始前に必ず確認すること

対局開始直前に、同一repositoryで実行中・queuedのGitHub Actionsを確認する。
これは現在の混雑状況と終了見込みを把握するためであり、空きが少ないから対局job数を減らすためではない。

開始後は実際のworkflow run IDを確認し、少なくとも次をユーザーへ報告する。

- 総対局数
- 条件数
- Shard/Lane数
- 投入job数
- runner利用方法（空き枠をGitHubが最大まで自動割当）
- 対局条件
- workflow run ID
- 終了予定時刻

## 3. 終了予定時刻

終了予定は、直近の同種対局workflowの実測時間を基準にする。
可能なら「同じ思考時間・同程度の局数・同程度のShard数」のrunを優先する。

終了見込みには、対局時間だけでなく以下を含める。

1. engine/opponent build
2. artifact受け渡し
3. queued時間
4. 対局
5. 集計・artifact upload

過去に比較可能なrunがない場合は保守的な見積もりを使う。

## 4. 結果確認タイマー

対局workflowのrun IDが確認できたら、**同じターンで終了予定時刻にChatGPTの結果確認タイマーを設定する**。
タイマー設定を後回しにしてはならない。

タイマー実行時:

- workflowが完了していれば結果を集計して報告する。
- 未完了なら、進捗と新しい終了見込みを報告する。
- 新しい終了見込みに合わせて再確認を設定する。
- ユーザーから指示がない限り、新しい対局を追加起動しない。

## 5. 例外

次の場合だけ並列数を意図的に抑えてよい。

- CPU/メモリ競合そのものを測る実験
- GitHub Actionsの利用量を抑えることが実験目的として明示されている場合
- 外部サービスへの同時接続数制限がある場合
- ユーザーがrunner数を指定した場合

例外を使う場合は、開始前に理由を明示する。

## 6. 2026-10-07の失敗からの固定ルール

Book+ExperienceのLv40/45/48/49/50/55再測定では、6レベルを6jobに固定し、各job内で4 laneを走らせたため、空きrunnerを最大利用できなかった。

原因は「空きrunnerを確認しなかった」ことではなく、**workflowが6jobしか生成しない設計だったこと**である。

以後、対局workflowはShard/LaneをActions jobとして外へ展開し、GitHubスケジューラが利用可能なrunnerを最大まで埋められる構造を標準とする。
