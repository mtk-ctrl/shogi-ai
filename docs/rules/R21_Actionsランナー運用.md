# GitHub Actions runner運用

## 目的
runner使用率ではなく、依頼された目的を最短・最大効率で完了する。

## 固定局数の対局
開始前に現在のActions実行状況と利用可能runner数を確認する。
停止してはいけない有効runが使うrunnerを除き、実際に空いているrunner数へ総局数をできるだけ均等に配分する。

- 原則1 Actions job = 1対局lane。
- 空きrunner数より多いjobを作り、意図的な2巡目待機を作らない。
- 空きrunner数より少ないjobでrunnerを遊ばせない。
- 目標は最後のrunnerの終了時刻を最小化すること。

## 時間枠型Nightly
終了時刻を定めた時間枠型は、固定局数と目的が異なる。具体的な夜間対局の期限はR30を参照する。
空きrunnerは原則最大限使うが、総局数だけを最大化せず、Nightlyで定めた研究生成・候補比較・検証・原因診断等の役割と状態継続性を守った上で、一晩の有効研究量を最大化する。

未実装フェーズを、runnerを埋める目的だけで別用途に勝手に置換しない。capability gapとして残す。


## 他workflowを止めてよい場合
runner確保だけを理由に別目的の有効runを停止しない。
停止してよいのは次だけ。
1. 同目的の旧runを修正版・再構成版が完全に置き換える。
2. 新しいrunにより旧runがobsoleteになり、旧結果が不要である。
3. ユーザーが明示的に停止を指示した。

## 起動時報告
run IDを確認したら、同じターンで少なくとも次を報告する。
- 総局数・条件
- 同時実行上限
- 他の有効runが使用中のrunner数
- 今回使うrunner数
- job/shard数と局数配分
- 局面知識の利用条件
- run ID
- 終了予定時刻

## Issue経由の対局起動と重複防止
R15のIssue方式では、**Issue作成、起動入口Workflowの成功、対局本体Workflowの起動、対局jobの実開始、最終結果の保存**を別段階として扱う。対象のIssue URLと起動入口run ID、対局本体run IDを対応付ける。
- 作成前に、同目的・同一条件の既存Issueと未完了runを確認する。受付応答が不明な場合も、先に既存IssueとActionsの状態を読み戻してから新規作成の要否を判断する。同一対局を二重起動しない。
- Issue本文の条件と実際に起動した本体runの条件（対局側A/B、固定commitまたはref、総局数、分割、時間、局面知識）を照合する。受付入口の `success` は対局完了を意味しない。`dry_run` は対局起動に数えない。
- 本体runのIDを取得できなければ、入口側の実行ログ・Actions一覧・入力検査結果を調べる。失敗した場合はR00/R15に従い原因を分類する。安全性の拒否を別経路で迂回せず、同じ要求を無条件に再登録しない。
- 最終報告では本体runと成果物を読み戻し、必要に応じIssueを完了として閉じる。期限付き成果物を長期保存済みと扱わない（R25）。確認タイマーが必要な場合は、同じ一連のタイマーで追跡する。

## 起動確認から結果確認までの一連タイマー
このタイマーは、**ユーザーから依頼された対局を「起動しただけ」で終わらせず、実際の開始確認から最終結果の報告まで取りこぼさず追跡するため**に使う。

ユーザー依頼の対局で、現在の作業ターン内に最終結果まで確認できない見込みなら、開始確認と結果確認を別々のタイマーに分けず、1本の確認タイマーを作成し、その同じタスクを更新しながら、起動確認 → 実行中確認 → 結果確認まで連続して扱う。

実装確認のためAI自身が起動した少数局のsmoke、CI回帰、短時間の内部検証など、**同じ作業の中で完了まで直接確認できるものにはタイマーを作らない**。その場でrunを追跡して結果を確認する。内部検証が想定外に長引き、ユーザーへ後で結果報告する必要が生じた場合だけ、この節の1本タイマー方式へ切り替える。

1. workflow起動・run ID確認と同じターンで、可能な範囲で実際の開始まで直接確認する。会話をまたぐ確認が必要なら、次の開始確認工程または終了見込み時刻に一回限りの予約を設定する。毎時等の反復予定を標準にしない。
2. 最初の発火では、対局job / shardが実際に開始したかを確認する。
   - queued / build中 / 対局未開始なら、原因・runner状況・同種のbuild/queue実測を確認し、次に確認すべき工程の妥当な見込み時刻へ同じタスクを更新する。未開始の対局の終了時刻を断定しない。
   - 対局jobが開始していれば、開始済みrunner数・shard数・進捗を確認し、最近の同種実測からETAを出す。
3. 対局開始を確認できたら、**同じ一回限りのタスクを終了予定時刻へ更新**して結果確認に引き継ぐ。開始確認用と結果確認用の2タスクを併存させない。
4. 終了予定時刻の発火で未完了なら、残局数・進捗・後処理を確認し、**妥当な新ETAへ同じタスクを更新**する。固定の2分・5分・毎時の反復へ自動的に置き換えない。
5. 失敗、aggregate未生成、artifact未取得等で最終結果を報告できない場合は、原因を確認し、安全に修正可能なら修正・再実行する。その場合も修正・再検証の完了見込みを根拠として同じタスクを更新する。
6. 最終結果を取得・報告できた時点で、その確認タイマーを停止する。一時Workflow等があれば整理する。

タイマーの目的は「対局workflowを起動したら儀式的にタイマーを置くこと」ではない。**ユーザー依頼の対局が本当に始まり、最終結果を報告できるまで、会話をまたいでも追跡責任を切らさないこと**である。現在の作業中に完了まで確認できるならタイマーは不要である。ユーザー指示なしに別対局を追加しない。

ETAは最近の同種実測を使い、build・queue・artifact等も含め、最後のrunnerが終わる時刻で見積もる。

### 一回限りの予定と提供機能の制約

終了見込み時刻に実行する一回限りの予定と、条件が成立するまで定期的に調べる反復監視を区別する。反復監視に間隔制限があることを、一回限りの予定も毎時にする根拠へ広げない。利用する機能の実際の制約・エラーには従い、短時間の一回限り予定を連続させて反復制限を回避しない。

本人が今回指定した運用は、実際の工程と進捗から終了見込みを出し、その時刻に一度だけ確認する方式である。未完了時は原因・進捗を読み直して新しい見込みへ更新する。対局が未開始の場合は準備や開始確認の予定であることを明示し、対局終了ETAと混同しない。

登録の種別を変更する際に提供機能が同じIDでの変更に対応していなければ、旧登録を無効にして一回限りの登録へ引き継ぐ。新旧IDと理由を台帳へ残し、有効な確認タスクは一つだけにする。この登録の置換を研究の完了・停止と扱わない。以後は引継ぎ先の同じタスクを更新する。


## 継続確認タイマーの正式運用（対局・研究・CI・PR統合共通）
この節は対局に限らず、将棋AI開発に関するすべての継続確認タイマーに適用する。

### タイマー作成・更新時の必須事項
- タイマーのpromptの**冒頭**に、次の指示をそのまま記載する。

> 最初にGitHubリポジトリ mtk-ctrl/shogi-ai の docs/00_開発ルーター.md を読み、そこから今回の作業に必要なactive Ruleをすべて読み直してください。ルーターとルールを読む前に状態変更・修正・CI操作・統合をしないでください。安全性チェック・ツール拒否・CI失敗では、ルールを確認し、原因を調査して許可された方法で修正・再実行してください。安全上の制限を回避しないでください。未完了の場合は、他の有効なrunnerを停止せず、同じ確認タスクの時刻を更新して追跡してください。完了を検証し結果を報告してから、このタスクを停止してください。

- 上記に続けて、対象リポジトリ・PR番号・ブランチ・run ID・成功条件・次に確認する内容など、再開に必要な具体的情報を記載する。
- タイマー作成・更新の直前に、promptに必須指示があることを確認する。更新でpromptを省略しても既存の指示が保持されることを確認し、欠けていれば補う。
- すでに登録されている確認タイマーも、次回更新時には同じ基準へ修正する。R00への記載だけで代用しない。

### 実行・終了条件
- 毎回の起動時にルーターと必要なactive Ruleを読み直し、現在のmain・PR・CI・runnerの状態を取得してから判断する。
- queued・失敗・検査未完了は作業完了ではない。原因調査、適切な再確認時刻への更新、許可された修正と再検証を行う。
- 完了の判定は依頼された成果物・統合commit・CI・保存記録等の読み戻しによる。起動しただけ、修正を送信しただけでは完了としない。
- 別目的の有効なrunnerを、待ち時間の短縮だけを理由に停止しない。
- タイマーを停止するのは結果報告後とする。ただしユーザーの停止指示や安全上の継続禁止がある場合はそれに従う。
