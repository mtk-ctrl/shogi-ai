# 基本原則

## 正本と優先順位
- 開発方針・仕様・運用の意図は、ユーザーとの会話で明示的に確定した内容を正とする。ユーザーの訂正とmdが食い違う場合、mdを理由に訂正を退けない。
- 同じ論点の変更・撤回・条件付き判断をたどり、最後に有効となった判断と適用範囲を確認する。検索で同じ言葉が見つかったことや、発言日時が新しいことだけを根拠に確定しない。
- 恒常的な方針、特定実験だけの条件、一時的な停止、未採用の提案を区別する。個別の条件を普遍的なルールへ広げない。
- AIの提案、推測、会話要約だけから新たな合意を作らない。元の発言を確認できない部分は、確認できた範囲と未確認部分を分ける。
- 採用済みの現行状態は `main` を正本とする。
- 未マージPR・研究ブランチは候補・実験であり、日時が新しくても現行ルールではない。
- `docs/rules/` の `status: active` は、会話で確定した現行運用を保存する場所である。activeの表示だけで会話との一致が保証されるわけではない。
- `journal/` は当時の記録、`docs/decisions/` は採用理由、`docs/archive/` は旧文書であり、現行Ruleを上書きしない。
- ファイル番号、保存日時、commit日時だけで「最新」を判定しない。
- 明示された特殊条件は一般Ruleより優先する。特殊条件かどうか不明なら、実装・Rule・採用記録を照合し、判断できなければ確認する。

## プロジェクトの方向
- 外部AIは先生ではなく物差しとして使う。
- 強化は Strength / Independence / Novelty を意識し、勝率だけで理由を見失わない。
- Engine / 局面知識 / Benchmark / Diagnosis の役割を混同しない。
- 外部AIの答えをそのまま模倣することを目的にしない。
- やねうら王から製品エンジンへ利用してよい範囲はルール層だけとする。詳細はR50を読む。

## 作業の原則
- ユーザーが指定した停止地点を越えて勝手に次工程へ進まない。
- 自動化できる反復作業は原則としてAI・GitHub Actions側で行い、人へ戻さない。
- 重大な曖昧さ、相反する現行根拠、保留事項は勝手に決着させない。
- 再利用する情報は「対局記録・研究記録・局面知識」の構成で扱う。旧Book / Experienceの概念は現行設計・エンジン・通常運用へ持ち込まない。
- ユーザー向け報告では、一般的でない内部変数名や英語略称をそのまま並べず、まず日本語で意味を示す。内部名は検証や実装確認に必要な場合だけ補足する。
- 会話で重要な訂正・決定があったら、R70・R90に従い確認記録と対象Ruleを更新する。md確認は判断が必要な論点を一問ずつ進め、簡易な文書更新・検査・main反映は区切りでまとめて行う。未保存の確定事項は確認記録の作業版に残し、保存済みと混同しない。

## タイマー・自動再開時の必須手順
- 将棋AI開発の確認タイマー・自動再開タスクは、毎回の実行開始時に `docs/00_開発ルーター.md` を最初に読み、そこから当該作業に必要なactive Ruleを読み直してから操作する。前回実行時の記憶やタイマー本文だけで作業を進めない。
- 安全性チェック・ツール拒否・CI失敗で停止した場合、直ちに完了不能として打ち切らない。まず該当Ruleを確認し、拒否された操作と原因を特定し、既存の許可された別手順で修正・再検証を試みる。安全上の制限を回避・無効化する操作はしない。許可された方法が尽きた場合のみ、具体的な障害と未完了事項を報告する。
- 継続確認タスクは未完了のまま停止しない。待機中・修正中は同一タスクの次回時刻を更新し、有効な別目的のrunnerを勝手に停止しない。最終結果の確認・報告後に停止する。ただし安全上の制限で継続そのものが認められない場合はそれに従う。
