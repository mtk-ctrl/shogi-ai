# Rule変更・同期手順

## ルーターの役割
ルーターにはRule本文を書かない。
ルーターを変更するのは、作業種別に対する「読む文書」が追加・削除・変更されたときだけとする。
Rule本文の数値・条件を変えただけなら、読み先が変わらない限りルーターを書き換えない。

## Rule変更時
会話で決まった変更は、先にR70の確認記録の作業版へユーザー発言と確定範囲を残す。簡易なmd更新は確認の区切りまたは引継ぎ前にまとめて下記手順で反映し、一問ごとのmain保存を義務にしない。ユーザーの訂正を、既存Ruleと違うという理由だけで未決扱いしない。
1. 変更対象のactive Ruleを更新する。
2. そのRuleが実装へ反映される内容なら、workflow / config / scripts / codeを検索して同期する。
3. READMEや設計文書に同じ現行条件が重複していれば、正本をRuleへ寄せ、必要なら参照だけにする。
4. 読み先が増減・移動した場合だけルーターを更新する。
5. 方針変更の理由が重要ならdecisionまたはjournalへ残す。
6. 旧文書に履歴価値があればarchiveへ保存する。
7. 最後に、旧値・旧パス・重複Rule・broken linkを検索する。
8. ルーターから到達する現役設計文書とREADMEを読み、active Rule・main実装と矛盾する「現在」「現行」「既定」「正式」等の記述が残っていないか確認する。特にrelease番号、対局時間、局面知識の利用状態、ACTIVE/HOLD/ARCHIVE workflowを照合する。
9. `python3 scripts/check_doc_router.py`、`python3 scripts/check_workflow_inventory.py`、`python3 scripts/check_match_workflows.py`、`python3 scripts/check_current_claims.py` を通す。
10. 採用済みの修正をmainへ保存し、対象commitの記録と反映先を読み戻す。

`.github/workflows/docs-rule-check.yml` も同じ検査を自動実行する。
これらの機械検査は参照先や既知の表現・設定を検査するものであり、過去の会話に対して事実が正しいことまで証明しない。会話との照合と、必要な本人確認を省略しない。

## 「最新」の判定禁止
次を単独の根拠に現行判定しない。
- ファイル名の番号が大きい
- 更新日時が新しい
- commitが新しい
- PRが新しい
- journalの日付が新しい

未マージPR・研究ブランチは、mainより新しくても採用済みではない。

## 衝突時
active Rule同士、Ruleとmain実装、またはRuleと明示的な採用記録が食い違い、意図を一意に復元できない場合は勝手に統合しない。
ユーザーへ論点を具体化して確認するか、保留領域へ隔離する。
