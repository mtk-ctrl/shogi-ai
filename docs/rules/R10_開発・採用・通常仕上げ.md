# 開発・採用・通常仕上げ

## 標準開発サイクル
1. 現行版の弱点を観察する。
2. 改善仮説を意味の分かる単位で立てる。
3. 実装する。
4. 必要な軽量テストを通す。
5. 必要な比較対局・診断を行う。
6. 採用・保留・撤回を判断する。
7. 採用内容と理由を記録する。

複数の大変更を同時に混ぜ、何が効いたか分からなくしない。

## 採用前
- 候補比較中に次版番号やAndroid表示だけを先行更新しない。
- READMEを候補版の状態へ書き換えない。
- 比較条件はR20に従う。

## 「通常仕上げ」
正式採用後の通常仕上げは次を1つの仕上げ単位として行う。
1. 採用コード・パラメータを反映する。
2. 必要な軽量テストを通す。
3. `journal/` に結果・条件・採用理由を残す。
4. READMEの現在地・採用値を必要な範囲で更新する。
5. 次回比較基準が変わる場合だけ `benchmarks/baseline_ref.txt` を更新する。

Android版表示、APK生成、Pixel/ShogiDroid2確認は通常仕上げに含めない。R60の条件でのみ行う。

既に採用判断に十分な比較を終えている場合、採用後に同じ100局等を理由なく再実行しない。

## Actionsの基本
- 日常変更は必要な軽量CIだけを自動実行する。
- パラメータ探索、大規模対局、一時実験、外部Benchmark等は原則手動起動とする。
- 関係ない変更で重いCIや通知を発生させない。
- 対局workflowの起動・分割・停止判断はR21に従う。
