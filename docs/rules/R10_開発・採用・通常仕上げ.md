# 開発・採用・通常仕上げ

## 標準開発サイクル
1. 現行版の弱点を観察する。
2. 改善仮説を意味の分かる単位で立てる。
3. 実装する。
4. 必要な軽量テストを通す。
5. 必要な比較対局・診断を行う。
6. AIが結果・根拠・懸念を報告し、オーナーが採用・保留・撤回を判断する。
7. 採用内容と理由を記録する。

複数の大変更を同時に混ぜ、何が効いたか分からなくしない。

## 正式採用の判断
2026-10-07の問8本人回答により、新しい研究候補はオーナーの判断なしに正式採用しない。
AIは依頼された範囲で仮説整理、候補実装、必要な検査・比較・診断、結果の整理、採用案の報告まで行う。
勝率が上がったこと、軽量テストが通ったこと、AIが有望と判断したことだけでは、正式採用を決定しない。数値調整だけの候補も同じ扱いとする。
研究・実装・検証を依頼されたことだけで、候補の正式採用が決まったとはみなさない。
正式採用前は候補として管理し、正式なmain Engine、既定パラメータ、世代表示、比較基準へ昇格させない。
本人の採否判断について、対象・条件・発言を記録する。採用が決まった内容の通常仕上げとmain反映はAIが行い、同じ保存許可を取り直さない。
既に本人が決めた内容の復旧・文書訂正・mainへの保存は、新候補の採用判断と区別する。許可済みの修正まで、このRuleを理由に毎回本人へ戻さない。
本人原文と判断の経緯は `docs/decisions/2026-10-07_会話による運用確認.md` の問8に記録する。

## 採用前
- 候補比較中に次版番号やAndroid表示だけを先行更新しない。
- READMEを候補版の状態へ書き換えない。
- 比較条件はR20に従う。

## 「通常仕上げ」
正式採用後の通常仕上げは次を1つの仕上げ単位として行う。
1. 採用コード・パラメータを反映する。
2. R70に従い、エンジン変更の大小にかかわらず正式版番号を進め、USIのエンジン名と現行説明・採用記録を同期する。文書だけの訂正や対局基盤だけの修正でEngine版を進めない。
3. 必要な軽量テストと現行説明の整合性検査を通す。
4. `journal/` に結果・条件・採用理由を残す。
5. READMEの現在地・採用値を必要な範囲で更新する。
6. 次回比較基準が変わる場合だけ `benchmarks/baseline_ref.txt` を更新する。

Android版表示、APK生成、Pixel/ShogiDroid2確認は通常仕上げに含めない。R60の条件でのみ行う。

既に採用判断に十分な比較を終えている場合、採用後に同じ100局等を理由なく再実行しない。

## Actionsの基本
- 日常変更は必要な軽量CIだけを自動実行する。
- パラメータ探索、大規模対局、一時実験、外部Benchmark等は原則手動起動とする。
- 関係ない変更で重いCIや通知を発生させない。
- 対局workflowの起動・分割・停止判断はR21に従う。
