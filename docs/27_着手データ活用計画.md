# 着手データの活用計画

## 決定と提案の区別
確定: 通常対局では実際に指した手と必要な評価・探索条件を蓄積する。未着手の候補手の通常保存は行わない。重要度と容量を考慮した保存項目・長期保存先・容量見直し基準の正本はR25、実装仕様は `docs/28_着手記録の保存仕様.md`。schema 2の収集・長期転送は未実装である。
「対局記録・研究記録・局面知識」の構成は本人承認済み。保存と最初の即活用経路の接続仕様は `docs/35_局面知識の統合設計と即活用.md`。研究時間、直接利用の具体的基準、正式昇格・自動更新等は引き続き提案・保留である。

## 記録から保存までの担当と処理順（2026-10-07確認）
以下の実装済みの経路は `benchmarks/arena.py` と `.github/workflows/engine-match.yml` の通常内部比較を指す。外部対局・位置指定対局・Androidまで同じ経路が接続済みとは扱わない。

| 順番・時点 | 実行する仕組み | 入力と処理 | 出力・現状 |
|---|---|---|---|
| 1. 起動・準備 | engine-match.yml の plan / build / match | 比較対象refを受け取り両エンジンをbuild。arenaへ実行ファイル、設定、go条件、seedを渡す | 実装済み。要求refと実際の確定commitを区別する記録は不足 |
| 2. 各手の思考 | 雲路エンジン | arenaの `Engine.bestmove()` が positionとgoをUSIで送る。エンジンは探索結果のinfoとbestmoveを返す | 実装済み。USIは通信規約であり保存機能ではない |
| 3. 各手の記録 | arenaの `parse_info_line()` / `compact_search_telemetry()` / `play_game()` | bestmoveを受けるまでinfoの値を更新して集める。合法な実戦手に手数・手番・A/B・評価・深さ・時間等を対応付ける | 実装済み。各手の `move_records` としてPythonのメモリへ追加。毎手のファイル書込みではない |
| 4. 対局バッチ完了後 | arenaの `main()` | バッチ全局のdetailsと、実行ファイルSHA256・設定・go条件・seedなどの共通情報をまとめる | 実装済み。ローカルの `results/shard-N.json` へ一括書込み |
| 5. バッチ完了後 | engine-match.yml の upload / aggregate と `tools/records/archive_played_moves.py` | shardをartifactに渡し、aggregateで回収。実戦手と手数を検査し、長期対象の項目のみ抽出して圧縮 | 実装済み。`played-games.jsonl.gz` と `manifest.json` を生成。PV・未着手候補を除外 |
| 6. 圧縮後 | engine-match.yml の Upload played-move archive（upload-artifact） | 圧縮記録とmanifestをGitHub Actionsの保存領域へアップロード | 実装済み。90日保存を要求する期限付きartifact。長期保存完了ではない |
| 7. 受渡し後 | 対局後の長期保存処理 | Releasesへ研究datasetとして移送し、取得し直したファイルのSHA256を照合する設計 | 未実装。保存先の選定はオーナーから委任済み。AIによる毎回の手作業を運用前提にしない |
| 8. 研究時 | 索引作成・検索・自作Analyzer | 圧縮記録から対局ID・手数・局面・エンジン条件を検索し、必要な局面を再解析する設計 | 共通着手アーカイブからの索引・研究経路は未接続。当時の評価は上書きしない |

### 一手ごとの情報と共通情報を結び付ける方法
各着手は `ply`（手数）、`engine`（A/B）、`move`、`search` を持つ。
現在の原JSONでは共通情報に `sha256_a/b`、`options_a/b` 等があり、A/Bから参照できる。
圧縮後は各局の `source_id` からmanifestのsource metadataへ辿り、A/Bから該当エンジンを識別する。
したがって「41手目を選んだエンジン、当時の評価、完了深さ、最大到達深さ」を同じ出所の記録として扱える。

完了深さdepthと最大到達深さseldepthは別物で、最大到達深さまで全候補の探索が完了した意味ではない。
局面知識を参照した手は、その知識だけで着手が決まったとは扱わない。局面知識の参照、一致、読み順変更と、今回の探索結果を別項目として記録する。
既存arenaはinfoを項目ごとに集約する。出力しなかった値や、選択方法・資産版を集約から推測して埋めない。

### 未実装部分を接続する設計
1. **準備時の出所確定:** Workflowのbuildで両エンジンの確定commitと実体ハッシュを記録する。対局開始時にはUSI識別名、実際の有効設定、局面知識の版・内容ハッシュ・件数を対応付ける。同じ内容の局面知識を毎局複製せず、資産の復元可否と対局との対応を記録する。
2. **各手の取得:** エンジンからbestmoveと対応する評価・完了深さ・最大到達深さ・時間・選択方法を受け取り、arenaが実戦手の行へ格納する。保存目的の再探索は行わない。局面知識を参照した場合も、今回の探索結果と知識参照の事実を分けて記録する。
3. **中断への備え:** 現状はバッチ完了時の一括書込みなので、途中例外や強制終了で全局分のファイルができない場合がある。完了した局ごとのチェックポイントを追加し、バッチ終了後に統合する設計。中断された局と完了局を区別する。
4. **対局後の永続保存:** 既存Workflowの対局後処理が圧縮・検査を呼び、同じrunと試行を識別できるファイル名でReleasesへ移送する。データ用releaseはエンジン製品版と区別する。再実行では同名・同hashなら二重保存せず、同名・異hashは上書きせずエラーにする。アップロード後の取得・hash一致で長期保存成功を確定し、失敗時はartifactを残して失敗を明示する。公開repoなので公開される研究データを対象とする。
5. **検索:** 保存単位ごとの対局数・欠損件数・ファイルhashとURLを一覧化する。局面索引は元記録から再生成できる派生物とし、同じ盤面と異なる到達履歴を区別して研究へ渡す。
6. **過去分の移行:** 残存するartifactを期限順に確認し、元のrun・ファイルhash・実戦手を保持して取り込む。保存済みの当時の評価は回収できるが、未記録の版・評価・深さは不明のまま残す。旧runのworkflow commitを対局エンジンのcommitと無条件で同一視しない。

この節は接続の設計であり、表の7・8や不足情報の収集が実装済みであるという報告ではない。
保存粒度・状態記録の扱い・評価種別の対応・容量台帳・検証条件は `docs/28_着手記録の保存仕様.md` を参照する。
局面知識への正式昇格基準、夜間対局の再開、通常対局の起動をこの整理だけで決定しない。

### 負担と確認方法
評価・深さを得るための再探索は不要だが、USI出力、受信、各手の記録にはCPU・メモリの負担がある。
既存arenaには合法手数・王手等の補助情報を計算する処理もあり、全収集負担をゼロと説明しない。
記録有無で同じ局面・同じエンジン・同じ時間条件を比較し、完了深さ、探索ノード、エンジン時間、USI受信までの実時間、対局プログラムの処理時間とメモリを測る。
圧縮・移送・索引作成は対局後に行う。負担の比較は未実施である。

## 長く蓄積し、雲路が更新される前提
全原記録は追記して残し、対局用の知識候補は現在の版に合う小さな別資産として作る。半年分を毎局読み込まず、月別保存・増分索引で必要な局面を取り出す。
古い深い手も研究材料に残すが、新版で確かめずに当時の評価や深さを移植しない。研究予算内で再登場・新旧の相違・不安定局面を優先し、固定した知識版で効果を確認する。
長期の保存・検索設計と容量点検の正本は `docs/29_着手データの長期運用と世代更新.md`。局面知識の正式採用・直接利用・自動更新は、R10・R25に従い別途検証して決める。

## 活用する順番
1. 局面ごとの新版比較: 同じ開始局面とそこまでの実戦手順を旧版・新版に渡す。同じ200ms条件と同じ固定深度条件を別々に比較し、着手・評価・深さ・時間・ノードの差を残す。比較目的に応じて局面知識の利用条件と初期状態を固定する。
2. 悪くなった着手の研究: 生の隣接評価をそのまま悪手判定にしない。固定した自作Analyzerで着手前と実戦手後を同条件で再評価し、着手者視点に戻す。再探索で得た別の手との比較は研究結果として分離する。
3. 深い解析結果の利用: 再登場局面、200msと1秒で手が変わる局面、評価が不安定な局面を研究対象とする。同じ雲路で1秒、必要なら5秒等へ段階的に延長し、選ばれた手・評価・深さ・条件を別解析記録にする。長く読んだことだけで最善・強化と認定しない。
4. 自前定跡: 研究手リストから序盤の連続した進め方と相手応手による分岐を研究する。狙い、適用条件、離脱局面、解析・実戦による根拠を添える。中終盤の単独研究は研究局面集として保持する。

## 研究記録
局面ID、開始SFENと到達手順、出所となる対局ID・手数、Analyzer実体ハッシュ・設定、解析条件、選ばれた研究手、評価・完了深さ、再解析日時を記録する。
通常対局の原評価を変更しない。研究中に未着手候補も比較・記録するかは研究モードの仕様として別途決める。

## 次の200msへの持込み
着手記録だけで以前の探索木の途中から完全再開することはできない。
通常の実戦記録や未確認の研究手は、過去に選ばれた手を先に探索する材料にする。
長時間研究を単なる候補提示以上に活用する案として、思考時間・完了深さ・条件を渡し、確認済み研究手を既定の着手へ置く方式を `docs/30_長考研究結果の着手への利用案.md` に具体化した。浅い探索だけで変更しない判定を比較検証する案であり、採用済みではない。
評価値の再利用・探索の打切り、探索を省く直接選択は、履歴・エンジン設定の互換性と別局面の検証を通すまで採用しない。
旧エンジンの研究結果は出所付きの候補として残し、新版で必要に応じ再確認する。

## 研究結果から評価・探索を改善する
長考の選択手を短時間でも選べるように、オーナーはパラメータ調整による本体改善を求めた。短時間手と長考手が異なる局面を研究し、評価の重み・項目定義・探索のどこを改善すべきかを調べる。
研究手を直接指す機能をOFFにして候補版自身の選択を測り、未使用局面・比較対局でも確認する。具体的な採用はR10に従いオーナーが判断する。
手順と限界は `docs/30_長考研究結果の着手への利用案.md` の「短時間で同じ判断へ届くよう本体を改善する」を参照する。今回は方針の記録であり、調整・比較は未実施である。

直近のnightly-research-raw-37524315123を取得した。200局・25,989実戦手、原JSON計23,438,699 bytes、元ZIP約1.84MB。
着手だけの新アーカイブは1,217,210 bytes。評価あり25,309手、欠損680手。欠損はゼロ補完していない。

## GitHub保存枠の確認（2026-10-07）
- 通常Git: 1ファイル100MiB上限。repositoryは1GB未満が理想、5GB未満を強く推奨。推奨値は無料枠の固定容量ではない。
- Actions: 公開repositoryの標準GitHub-hosted runnerは無料扱い。非公開repository向けのFreeプランartifact枠500MBを、この公開repositoryの長期保存総量上限として扱わない。artifactは期限付きの一時受渡しとする。
- Git LFS: Freeは保存10GiB・ダウンロード帯域月10GiB。毎回全データを再取得する運用には帯域の考慮が必要。
- Releases: 1ファイル2GiB未満、1release最大1000assets、総容量・配信帯域に公表上限なし。ソフトウェアに付随する研究dataset・知識版の長期保存先として設計を採用。無制限のバックアップ倉庫とみなさない。

## 概念統合後の即活用
出所付きの原本から現在の雲路向け局面知識を作る。定跡は局面知識のうち序盤の手順・分岐を整理した部分とする。
採用済み局面知識を探索開始時の読み順へ使う機能は実装済みである。一方、新しい対局・研究記録から候補を自動生成して正式な局面知識へ加える処理は未接続である。
docs/35は原本→条件と履歴の確認→小さな固定知識候補→対局前読込み→rootの探索順反映を具体化する。長考研究の直接利用は別モードとして条件を詰める。
