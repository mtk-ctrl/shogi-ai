# 開発運用と評価フロー

## 目的

AIを強くするたびにPixelでAPKを入れ直して人間が確認する運用にはしない。
普段の開発・比較はGitHub上で行い、人間の実機確認はユーザーが必要としたときだけ行う。

## 通常の流れ

```text
戦略コードを変更
  ↓
Quick Strategy CIでビルド・軽量テスト
  ↓
必要なときだけ比較対局workflowを手動実行
  ↓
勝率・合法性・速度などを確認
  ↓
採用判断
  ↓
採用内容を実装・journal・READMEへ記録
  ↓
次の開発へ進む
```

Pixel/ShogiDroid2での実機確認は通常の流れから切り離す。ユーザーが実機確認を求めたときだけAndroid仕上げを行う。

## 採用判断後の仕上げルール

採用判断より前に、次版のバージョン番号やAndroid表示だけを先行して変更しない。
候補比較中は、エンジン本体・README・Androidの版表示を現行採用版のまま維持する。

パラメータや小規模な戦略変更を正式採用した後は、まず必要最小限の通常仕上げを行う。

1. 採用されたコードまたはパラメータを反映する。
2. Quick Strategy CIなど必要な軽量テストを1回通す。
3. `journal/` に結果・採用理由・比較条件を記録する。
4. READMEの現在地と採用値を更新する。
5. 次回比較の基準が変わる場合は `benchmarks/baseline_ref.txt` を採用版へ更新する。

Android側の版表示更新、APK生成、Pixel/ShogiDroid2での実機確認は通常仕上げに含めない。ユーザーが「Pixelで試したい」「APKを作って」など実機確認を求めたときにだけ行う。

同じ目的の変更を理由なく1行ずつ別工程へ分割しない。利用するツールの制約で内部的に複数ファイルを扱う場合でも、可能な限り1つの仕上げ単位としてまとめ、各変更ごとに重い検証を繰り返さない。

既に採用判断に十分な比較が完了している場合、採用後に同じ100局対局をやり直さない。Android APK生成、Sanitizer、フルCI、Experience Cache専用ベンチも自動的には追加しない。

ユーザーから「結果が出たら一度止める」など作業境界の指定がある場合は、その地点で停止し、journal更新・版上げ・APK生成など次工程へ勝手に進まない。

## GitHub Actionsの起動方針

通常のコードpushで常時自動起動するのは **Quick Strategy CI** とする。機能別CIは関連パスが変わった場合だけ自動起動してよい。

- `Quick Strategy CI`：日常のpushで自動実行。ビルド、strategy test、move ordering testを短時間で確認する。v0.0.14からは可変深度探索とUSI出力・時計・停止、v0.0.15からは静止探索の独立minimax・王手回避・中断試験も含む。
- `Kifu Learning CI`：棋譜学習前処理に関係する `tools/kifu/**`、専用tests、`scripts/build.py`、workflow自体が変わった場合だけ自動実行する。通常の戦略変更だけでは起動しない。
- `Engine Benchmark`：手動実行。旧採用版との対局が必要なときだけ起動する。
- `Experience Cache Benchmark`：手動実行。Experience Cache自体を変更・検証するときだけ起動する。
- `Experience Cache Persistence`：手動実行。永続化処理を変更・検証するときだけ起動する。
- Android/APK/Sanitizer系：通常pushでは起動しない。Android更新または実機確認が必要なときに手動実行する。

評価値探索や特定機能の比較用workflowも、通常開発のたびに自動実行させない。必要な実験を明示して起動する。

## Pixel側の更新

Pixel/ShogiDroid2で実機確認するためのAndroid仕上げは、ユーザーから依頼があった場合に行う。
その際はエンジン名・Android `VERSION`・`versionName` / `versionCode`・ランチャー表示・OEXエンジン名をまとめて整合させる。

AndroidのApplication IDは `com.mtkctrl.shogiai` のまま固定する。
GitHub Actionsで同じ開発用テスト証明書を使ってAPKへ署名する。
versionCodeは必ず増加させる。

この方式へ切り替える最初の1回だけ、従来の別署名APKをアンインストールする必要がある。
その後は原則として新APKを開き「更新」するだけでよい。

開発用テスト鍵は公開前提であり、本番配布には使用しない。

## ShogiDroid2

APK更新後、ShogiDroid2が保持しているOEXエンジンのコピーが自動的に更新されるとは限らない。
実機検証時に「更新」または再コピーが必要かを確認する。
日々の戦略比較にはShogiDroid2を使わない。

## 自動対局

`benchmarks/arena.py` は2つのUSIエンジンを同条件で対戦させる。
先後を交互にし、合法手は独立実装 `python-shogi` でも検査する。
不正着手が1つでもあればベンチマークを失敗させる。

`benchmarks/baseline_ref.txt` には現在の比較基準となる採用版コミットを1つ固定する。
新しい戦略を採用したときだけ基準コミットを更新する。

通常pushでは比較対局を自動実行しない。比較が必要な変更だけ `Engine Benchmark` 等を手動起動し、局数は実験目的に応じて決める。少数局だけで強さを断定しない。

## 人間が行うこと

- Pixel/ShogiDroid2での実戦確認を行うかどうかの判断
- 棋力・指し味・不自然な手の評価
- 大きな方針判断

それ以外のビルド、合法性検査、比較、結果集計は可能な限りChatGPT・GitHub Actionsで行う。

## 比較記録の補足（v0.0.3から）

全着手、終局SFEN、乱数seed、最大手数、実行ファイルのSHA-256、応答時間をJSONへ記録する。
棋譜は `benchmarks/results/`、判断は `journal/` に残す。
比較プログラムは千日手と連続王手を区別し、入玉宣言も独立検証する。合法手なしは王手の有無によらず手番側の負けとする。

v0.0.13までの比較では `go movetime 1` を送っていたが、旧版は厳密な1ms制限を実装していなかった。v0.0.14では固定深度の回帰確認に `go depth 3` を用いる。v0.0.15以降、戦略の採否を測る通常比較は原則 `go movetime 50` とし、固定深度は同一探索結果の回帰確認に使い分ける。`--go-command` で条件を明示する。
10秒の応答監視は停止検出用であり、持ち時間制の強さを示す試験ではない。50〜500msの比較では少なくとも500msまでは追加時間による棋力向上を確認しているが、日常の戦略比較は開発速度を優先して50msを基準とする。
応答時間にはUSI通信と初期局面からの棋譜再現も含むため、評価関数だけの計算時間とは区別する。
