# 検証ジョブ並列運用ルール

## 原則

複数チャット・複数テーマからGitHub Actionsの検証を同時に投入することがある。
新しい検証を開始したことを理由に、既に走っている別の有効な検証を自動キャンセルしない。

### 自動キャンセルしてよい場合

- 同一目的・同一データ取得の検証を、実装ミス修正やrunner分割改善などで明示的にやり直す場合
- 古いrunの結果を使わず、新しいrunで完全に置き換えることが明確な場合

### 自動キャンセルしてはいけない場合

- 別テーマの検証
- 別チャットから開始した独立実験
- 比較対象・条件・目的が異なる実験
- 途中結果にも価値がある長時間実験

## 実装方針

研究用workflowは原則として `cancel-in-progress: true` を使わない。
既存workflowを再利用する場合も、現在同じconcurrency groupで走っているrunを確認してから投入する。

runner枠が埋まっている場合は、既存runを止めず、新しいjobをqueueさせる。
高速化のために既存runを置き換える場合は、そのrunが同一目的であることを確認してからキャンセルする。

## 例

2026-10-07のB/C robustness試験では、11 runner構成を20 runner均等分割へ変更した。
これは同一目的・同一2,200局を高速に取り直す置換だったため旧runのキャンセルは許容された。
今後、別検証が同時に動いている場合は同様に扱わない。
