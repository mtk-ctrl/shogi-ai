# 局面知識の統合設計・保存・次回対局への利用

## 決定範囲と現状
2026-10-07、オーナーは「対局記録・研究記録・局面知識」の構成で進めることを承認し、保存方法と即活用方式の具体的な保存を依頼した。2026-10-08、旧Book / Experienceの概念と実行機能を現行エンジンから外すことを追加決定した。
方針の正本は `docs/rules/R25_着手記録の保存.md`。詳細保存項目はdocs/28、長期運用はdocs/29、長考結果を着手判断へ使う検証案はdocs/30。
本書は接続する実装仕様である。2026-10-08、採用済みsnapshotのmaterialize、loader、root move ordering、利用telemetryまで実装した。新候補の自動正式昇格と夜間再開は別である。2026-10-08、採用済み研究手の直接着手と相手応手が研究筋に一致する間の継続採用をエンジンへ追加した。

| 構成 | 保持する内容 | 性質 |
|---|---|---|
| 対局記録 | 実際に指した全手、当時の評価・深さ・時間・条件・出所 | 追記する原本。通常の未着手候補・PV・探索木は長期保存しない |
| 研究記録 | 選んだ局面を長く読んだ結果、版比較、原因手研究、確認状態 | 別の原観測。対局時の評価や旧研究を上書きしない |
| 局面知識 | 今の雲路に渡す選択手、読みの量、適用条件、原本への参照 | 原本から再生成できる小さな対局用資産 |

対局由来か研究由来かは出所属性として保持する。
「定跡」は局面知識のうち、序盤の連続手順・相手応手による分岐・狙い・適用条件を整理した部分を指す。中終盤の単独研究も局面知識へ含む。
旧実装の過去記録は履歴として残すが、現行エンジンのUSI設定・着手処理・永続資産としては使用しない。

## データを保存する具体的な手順
| 時点 | 担当する仕組み | 保存・処理 |
|---|---|---|
| 起動前 | 既存Workflowのbuildと対局プログラム | 確定commit・実体hash・有効設定・CPU・go条件・知識版を共通profileへ登録 |
| 各着手 | 雲路のUSI出力と対局プログラム | 採用した完了結果の手・評価・depthを一組で取得。seldepth・nodes・両時間・決定元等を実戦手へ対応付ける |
| 一局終了 | 対局プログラム | 全実戦手・終局・集約統計を完了局チェックポイントへ書く。中断局は区別 |
| バッチ終了・回収 | 共通圧縮・検査処理 | gzip JSONLとmanifestを作成。指し手・手数・出所・欠損・hashを検査 |
| 対局後 | 既存Workflowから呼ぶ長期保存処理 | 月別データReleaseへrun/attempt/partを追記。取得し直したhash一致で長期保存成功を確定 |
| 保存確認後 | 増分索引・容量台帳・知識生成処理 | 新規partだけ局面復元して索引へ追加。現行版向け知識候補を生成し、実測容量を記録 |
| 研究後 | 自作Analyzerと同じ保存処理 | 研究IDと条件を持つ別JSONLを追記し、知識候補の根拠へ追加 |

共通profileは毎手に複製しない。毎局面のSFENは開始SFENと全実戦手から復元する。原本のJSONLにはschema版を付け、既存schema 1もreaderで保持する。
評価のcp/mate・値・境界はまとめて更新する。欠損はunknown、旧記録の判別不能な値はambiguousとし、0や推測値を補わない。
今回の探索評価が最終採用手に対応しない場合、採用手の現在評価を捏造せず、過去研究への参照と今回の観測を分ける。

### 保存の入れ物と容量
原本はGitHub Releasesのデータ用release。JST月ごとに整理し、run終了後に移送する。Engine製品releaseや通常Gitへの大量commitと混ぜない。
圧縮partは256MiBを超える前に分割。同名・同hashの再送は検証して重複保存せず、同名・異hashは上書きしない。
共通資産は内容hashで共有し、復元可否を明記する。可変知識の全snapshotを毎局作らない。
Actions artifactは期限付きの受渡し。現行の内部比較圧縮記録は90日要求であり、自動長期移送が動く前に期限を短縮しない。
通常記録平均6KiB/局、一時artifact100MiB、長期累計初回1GiB、以後5GiB・10GiB・倍増を点検目安とする。固定上限・自動削除基準ではない。
通常棋譜・研究・資産・索引・局面知識・一時Rawの実bytesを分け、月次で30/180/365日予測を更新する。原記録の間引きで容量を調整しない。

## 即活用する最初の方式: 過去の選択手を先に読む
最初に接続する経路は `move_order_hint`。通常対局・長考研究で選ばれた手を、次の探索の有力な手として優先する。
研究手と同じ結論を200msで再現する保証はないが、探索順を改善して枝刈りや完了深さを改善できる可能性を検証する。
古い評価への加点、旧評価を使ったcutoff、探索木の再開はこの方式へ混ぜない。研究時間は読みの量として渡し、時間に比例する評価加点をしない。

### 原本から局面知識候補を作る
1. 取得hashを確認した新規原本を逐次読み、開始SFENから実戦手を再生する。実戦手は着手直前の局面へ対応付ける。研究は明示した研究開始局面へ対応付ける。
2. 出所が知識利用対象か確認する。人間の棋譜はR50によりオーナー本人との対局だけ。外部AIの評価・推奨手を混入させない。外部AI対局での雲路自身の観測は、2026-10-08の本人判断により知識候補の対象に含める。出所・版・条件を保持し、この部分判断だけで候補を正式採用・自動更新しない。
3. 完了した通常探索または自作研究の選択手を候補にする。合法性と手・完了結果の対応を確認する。探索を省略した直接選択、代替手、深さ0、部分探索、出所不明、曖昧な完了結果を「深く読んだ手」へ昇格させない。
4. 初回仕様は対象commit・実体hash・有効な評価/探索設定・ルール・知識条件が照合できる範囲に限定する。条件欠損を同じ設定と推測しない。旧版・不明条件の記録は研究材料に残す。
5. 同じ局面・同じ条件で同じ手なら根拠を集約する。異なる手なら深さ・時間だけで正解認定せず相違ありを付ける。初回は相違のある候補を自動投入せず研究待ちへ回す。
6. 同じ尺度の完了深さ・ノード・確認状態・利用頻度等で候補を選び、小さな固定snapshotを生成する。64MiBは追加常駐メモリの初期検証目安。全原本を毎対局読み込まない。
7. 構文、hash、対象profile、合法性、メモリ上限を検査し、知識版と入力manifest集合hashを確定する。生成・検査済み候補と正式採用版を区別する。

### 局面知識のレコード案
ファイル仕様 `position-knowledge-v1` は局面知識専用形式であり、旧形式との互換を前提にしない。

| 情報 | 具体的な内容 |
|---|---|
| 検索キー | 駒配置・双方の持駒・手番・ルールID。外部のhashを雲路内部hashへ無検証で流用しない |
| 履歴条件 | 研究の開始SFEN・到達手順は出所・再現用として保持するが、直接着手の入口は駒配置・持ち駒・手番で照合する。反復履歴がある場合のみ履歴依存の安全性を優先して通常探索へ戻す |
| 選択手 | USI表記の手。根拠となる完了結果と対応 |
| 読みの量 | depth・seldepth・nodes・報告時間・実測時間。研究は制限時間と採用完了結果時点も区別 |
| 適用profile | 確定commit・実体hash・有効設定・ルール・知識状態の参照 |
| 扱い | mode=move_order_hint、確認状態、相違・適用外理由 |
| 根拠 | game ID＋着手直前ply、またはresearch ID、原本part hash、日時 |
| 知識版 | schema・生成器commit・入力集合hash・選択条件hash・知識ファイルhash |

根拠の評価と詳細条件は原本へ辿れる。今回の探索を打ち切る評価値としてloaderへ投入しない。
盤面や履歴の共通情報は参照で共有し、利用時に必要な照合情報は対局前にローカルへ読み込む。

### 次の対局で使う
- 対局開始前にWorkflow/runnerが指定した知識候補または採用版を取得・hash検査する。エンジンは対象profileを確認して読み込み、固定した知識版を対局へ対応付ける。
- エンジン側loaderは正規化した局面から自作ルール層を使って内部キーを生成する。探索開始時に局面と履歴条件を確認し、手が合法ならrootの読む順番へ反映する。初回の接続はrootを対象とし、内部ノードへの拡張は別検証とする。
- TTや今回の反復深化で得た最新の有力手も探索順に使う。過去の手を全探索で必ず一番に固定する規則にはしない。
- 今回の完了探索が最終着手を決める。hintを参照した事実と、そこから最終手が決まったかは別に扱う。
- 手ごとにファイル取得・展開・原本検索は行わない。参照と照合の時間は今回の200ms予算へ含め、hint欠損・破損・条件不一致なら通常探索へ戻る。
- 固定snapshotは対局中に差し替えず、新しい観測は次の知識候補へ回す。比較では両者のsnapshot・初期状態・可変cache設定を固定して条件を揃える。

「即活用」は再研究を必須にせず次に開始する対局バッチへ候補を渡せることを指す。全局・全手への無条件採用ではない。
新しい対局記録・研究記録から局面知識候補を自動生成する経路は未接続であり、保存した全記録が自動的に次局へ利用されるとは報告しない。
候補の生成・検査は自動化できるが、検証していない知識版を正式採用へ自動昇格させない。採用済みの局面知識は通常対局で毎回利用する。候補試験から正式な局面知識への更新判断はR10に従う。研究結論を直接着手へ使う方式は2026-10-08に正式採用された。

## 長考した結論を着手判断に使う経路
`research_decision` は局面知識の別の利用モードとして設計する。1時間の研究手を200msの浅い相違だけで変えない案はdocs/30に従う。
研究筋の直接採用は2026-10-08正式採用済み。2026-10-10に、同一局面へ別手順で到達した場合でも研究手を直接採用するよう修正した。入口では盤面・持ち駒・手番と合法性を検査し、反復履歴がある場合は通常探索へ戻す。研究手の次の着手以降は、相手応手と**実際の**到達履歴が研究筋に一致する場合だけ継続採用する。新候補は無条件昇格しない。
使用する場合は研究IDと当時の時間・深さを参照し、今回の探索結果とは分ける。旧研究値を今回の探索値に見せない。

## 効果をどう確認するか
同じエンジン・対象局面・履歴・初期状態で、知識なしとmove_order_hintありを比較する。
通常200ms＋AdaptiveLongThinkの正式条件と、固定200msの診断を分ける。完了深さ・探索ノード・cutoff・参照負担・総応答時間・選択手・独立した比較対局の成績を測る。
長考手への一致率だけを強化の証明にしない。研究に使わなかった局面・後日の対局でも確認する。
欠損、旧版、反復履歴あり、制限候補外、違法手、破損snapshotは通常探索へ戻ること、同一盤面へ異なる合法手順で到達しても研究手を直接採用することを確認する。
利用統計は局ごとに集約し、選択した知識の出所を必要な手で小さく参照する。全候補・全探索木を長期保存する要件にはしない。

## 実装順と現在地
1. schema 2と完了局チェックポイント、採用手に対応するUSI観測を接続する。
2. 共通の長期保存・取得hash確認・容量台帳を接続する。
3. 原本から増分索引とposition-knowledge-v1候補生成器を作る。
4. エンジンloaderとrootのmove ordering、出所telemetryを既存の自作処理へ接続する。
5. 同じ版・固定知識で負担と効果を測り、採用案を提示する。
6. research_decisionの基準を詰め、別に試作・比較する。評価・探索の本体改善はdocs/30の方針を並行して進める。

現在はschema 1圧縮＋内部比較の一時保存、採用済み `position-knowledge-v1.tsv` の生成、読込み、探索開始時の読み順反映、利用統計が実装済み。初期snapshotは完了した60秒研究のうちdisputed 7局面を除く53局面である。単独研究29局面も、採用済み研究集合に含まれる限り直接採用の対象とする。標準Actionsでは外部snapshotを固定配布し、Android/OEX・単体実行では標準ファイル欠損時だけ同じsnapshotのバイナリ埋込版へfallbackする。
schema 2、局ごとのチェックポイント、Releases自動移送、増分索引、新アーカイブからの自動候補生成・自動昇格は未実装。採用済み研究手の直接着手と読み筋継続は実装済み。
