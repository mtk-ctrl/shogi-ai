# 対局Workflow Build失敗の原因と再発防止

## 調査結果

2026-10-08、直近の対局・局面研究Workflowの失敗を実行ログまで確認した。
頻発していた失敗の主因は現行EngineのBuild不能ではなく、通常の内部比較で利用できる `.github/workflows/engine-match.yml` を使わず、一時WorkflowへBuild・依存導入・seed・artifact処理を繰り返し複製していたことだった。

確認した代表例は次のとおり。

- run 37630423219: Build成功後、seedがUSI signed-int範囲を超え、全match job失敗。
- run 37672066462: Engine Build成功後、`\\${{ github.run_id }}` の誤escapeによりartifact名へbackslashが入り失敗。
- run 37679032209: リポジトリrootに `CMakeLists.txt` がないのに `cmake -S . -B build` を使用し失敗。
- run 37680335520: Build方法修正後、`python-shogi` 未導入で `ModuleNotFoundError: No module named 'shogi'`。

一方、標準Build方法の `scripts/build.py`、`python-shogi==1.1.1`、seed事前検査等を持つ汎用対局基盤では、v2系と旧版の比較を正常に完走した実績がある。

## ルーター上の原因

`docs/00_開発ルーター.md` は「GitHub Actionsで対局を起動・分割・監視」についてR20/R21だけを読む構造だった。
既存Workflowを再利用するか専用Workflowを作るかを決める正本はR15であるため、ルーターを読んでもR15へ到達しない経路が残っていた。

加えて、一部の対局作業では専用ルーター・Rulesを先に確認せず、一時Workflowを直接作成した。
したがって原因は「ルーターの読み先不足」と「ルーターを通らない実行」の両方である。

## 採用した再発防止

1. 対局Actionsのルートを **R15 → R20 → R21** に変更した。
2. 局数、ref、持ち時間、USI option、shard数だけの差は、原則 `engine-match.yml` の入力で表現する。
3. 専用Workflowは、独自matrix、段階研究、Position Bank、Diagnosis等、実験構造が既存基盤で表現できない場合に限定する。
4. 専用対局Workflowは初回に `workflow_dispatch` を残し、pushだけを初回実験開始の合図にしない。
5. `scripts/check_match_workflows.py` を追加し、次を事前検査する。
   - GitHub Actions式の誤escape
   - 明白なseed範囲超過
   - arena実行時のpython-shogi導入
   - 存在しないroot CMake入口
   - 標準engine-matchのbuild.py、seed検査、game_offset等の契約
   - 専用arena Workflowのself-preflightとworkflow_dispatch
6. `tests/test_match_workflow_guard.py` で今回確認した失敗型を回帰テスト化した。
7. `docs-rule-check.yml` へ上記検査を組み込み、Workflow変更を含む全branchのpushで検査する。

## 運用上の意味

今後の通常比較では、対局条件をYAMLとして毎回書き直さない。
専用Workflowが本当に必要な研究でも、今回のような周辺設定ミスは重い対局jobへ進む前に検出する。

この変更はEngineの探索・評価・対局条件を変更しない。対局起動経路とWorkflow品質保証だけを変更する。
