# 着手記録の保存仕様

## 位置付け
2026-10-07のオーナー依頼に基づく、重要度と容量を考慮した保存設計。運用範囲の正本は `docs/rules/R25_着手記録の保存.md`。
本書は次の収集・保存形式（schema 2）の実装仕様である。現在の圧縮ツールはschema 1であり、本書を書いただけで新項目の収集や長期転送が動くわけではない。
Book / Experienceへの研究結果の昇格や、夜間研究の再開は本書で決定しない。
月単位・半年以上の蓄積、増分索引、Engine更新、対局用知識の容量分離は `docs/29_着手データの長期運用と世代更新.md` に従う。

## 目的から必要情報を決める
| 目的 | 欠かせない記録 | 利用方法・限界 |
|---|---|---|
| 出会った局面の読みを効率化する | 開始局面、実戦手順、選ばれた手、完了深さ、時間、エンジン・設定・知識状態 | 同じ局面で過去に深く読んで選ばれた手を探す。探索木の途中から完全再開する資料ではない |
| エンジンの新版と旧版を比較する | 両者の確定commit・実体hash・有効設定、局面への到達履歴、探索条件、当時の評価・深さ・時間・ノード | 同じ局面と条件で再解析し、旧観測と新版研究を並べる。版名だけで同一エンジンと扱わない |
| 悪くなった着手を研究する | 全実戦手、当時の評価の視点と出所、勝敗・終局理由、出所となる局・手数 | 前後局面を固定した自作Analyzerで再評価する。隣接する異なるエンジンの生の点数だけで悪手と決めない |
| 長く読んだ結果を蓄積する | 研究局面・到達履歴、Analyzerの識別と条件、選ばれた研究手・評価・深さ・時間 | 実戦の記録とは別の研究記録へ追加する。実戦時の評価を上書きしない |
| 自分たちの定跡を作る | 序盤の実戦手順と研究結果、相手の実戦応手、適用条件、根拠への参照 | 複数局に実際に登場した分岐を組み合わせる。未着手候補を毎対局で全保存する必要はない |

## 保存する項目と粒度

### 1. 全実戦手の必須項目
毎手の行を小さく保つ。完了したすべての対局の全実戦手を残し、勝局だけ・重要局面だけへ間引かない。

| 項目 | 形式・扱い | 残す理由 |
|---|---|---|
| 実際の指し手 | USI指し手文字列。リスト順が手数 | 棋譜・前後局面・分岐を復元する |
| 評価 | `status`, `kind=cp/mate`, `value`, `bound=exact/lower/upper/unknown`。視点は思考開始時の手番側に統一 | 当時の判断を研究・版比較へ使う。詰みと通常評価を混ぜない |
| 評価の出所 | `search/book/mate_solver/unknown` | Book由来の値などを探索評価と混同しない |
| 完了深さ・最大到達深さ | `depth`, `seldepth`。出力がない場合は欠損 | どこまで完了し、どこまで一部を読んだかを区別する |
| 時間 | エンジンが報告したmsと、対局プログラムが観測した往復ms | 読みの長さと通信等の負担を区別する |
| 探索ノード数 | 整数。npsは時間から算出し重複保存しない | 同じ時間で進む量、探索誘導の効果を調べる |
| 手の選び方 | `search/book/mate_solver/fallback/unknown` | 通常探索・Bookによる直接選択・詰み専用処理・読み未完了を区別する |
| 長考 | 使用したか。使用時だけ理由を記録。基本時間・最大時間・回数上限は共通設定 | 200msと延長された手を分ける |
| 終了・中断理由 | `time/nodes/depth/stop/book/mate/fallback/unknown`等。取得できる事実だけ | 深さ上限到達と時間切れ・未完了を区別する |
| 各手の時計・制限 | 固定go条件なら共通情報への参照のみ。実際のgo条件が変わる対局ではその手の時計・増分・制限 | 持ち時間が変わる対局でも当時の条件を失わない |

手数、手番、A/Bは開始局面の手番、実戦手の順序、局ごとの先後割当から復元できるので、schema 2では毎手に重複保存しない。途中開始でも開始SFENと割当から復元する。収集・検査中は明示値を使って整合性を確認する。
先手視点の評価値も毎手二重保存せず、手番側評価と手番から算出する。
通常の実戦手以外の投了・入玉宣言・反則応答は、対局末尾の終局観測へ分ける。違法な応答を実戦手として盤面に適用しない。

### 2. 対局ごとに一度残す項目
- 対局ID、元run/attempt/job/shard、局の通し順、UTC開始・終了日時、通常比較・研究対局・外部対局等の区分。
- 明示した開始SFEN、先手・後手のエンジン設定ID、各エンジンのseed。
- 全実戦手、勝敗、終局理由、完了・中断の区別、最終SFEN、終局観測。
- 各エンジンのセッションID、局順、知識状態の継承・リセット・読込みイベントへの参照。
- TT / Experienceのprobe・hit・並べ替え回数、通常探索・静止探索のノード・cutoff等は、取得できるものを**局ごとの合計**として残す。利用統計の欠損は0としない。
- 実戦手と末尾の投了探索の統計を区別する。

### 3. 同じ条件なら一度だけ残す共通情報
各対局がIDで参照する。大きな設定やhash文字列を全着手へ繰り返さない。
- **エンジン設定:** 表示名、正式世代ラベル、実際にbuildした確定commit、実行ファイルSHA256、build設定・コンパイラ・依存版、実際に有効なUSI設定。Android完成版番号をEngine世代の代用にしない。
- **対局条件:** go条件・時計ルール、長考設定、最大手数、判定ルール版、乱数の決め方、対局プログラムcommit、収集schema版。
- **実行環境:** runnerのOS・CPU名/割当CPU数・architecture、同時対局数・スレッド数。実行ごとに一度でよい。
- **知識資産:** Book / ExperienceのON/OFF、資産ID、元ファイルまたは埋込み資産のSHA256、版・source commit、可変・固定の区別、初期状態、復元先、復元可否。
- **保存manifest:** 元ファイルhash、圧縮ファイルhash・bytes、対局数・手数・欠損数・曖昧評価数、資産の物理bytes、保存URL、公開範囲、移行元と保存確認状態。

### 4. 容量を使わず復元・再計算する情報
毎局面の盤面SFEN、同一局面のhash、王手、駒取り、成り、駒打ち、合法手数、駒の効き、玉の守り等の特徴量、各評価項目の内訳は、全対局の全手に重複保存しない。
盤面と履歴は開始SFEN＋指し手から復元する。局面hashと検索索引は対局後に生成する。
特徴量や静的評価内訳は、**明示した評価コード版**で計算する。新版での再計算を当時の値として扱わない。旧版での再計算ができない場合は復元不能とする。
研究で必要になった局面の内訳は、その研究記録にコード版付きで残す。

### 5. 通常の長期保存に入れない情報
- 指さなかった候補手、PV、探索木、置換表の全内容、USI全文ログ、反復深化の全途中経過。
- 毎手のBook / Experienceファイル全体、毎局面の全特徴量、同一内容の棋譜をJSON・CSA・KIFの三形式で重複保存。
- 全試作エンジンの実行ファイルコピー。確定commit・build条件・hashを残し、採用版・重要な再現対象の実体は既存release等へ一度だけ保管する。

診断用Rawやログは期限付きの一時保存であり、通常着手アーカイブの正本とはしない。過去に保存した原記録は、この設計を理由に破棄・書換えしない。

## Book / Experienceの実体はどう残すか
Bookは同じ内容を資産hashで共有し、Gitにある原本commitや既存releaseで復元できれば参照を使う。復元できない独自資産だけ、一度圧縮保存する。
Experienceは容量と変化量が大きくなりやすい。毎手・毎局の全コピーはしない。通常はセッション開始の初期状態を一度保存/参照し、局順と読込み・リセット・継承・更新設定を記録する。終了時に取り出せる状態のhash・件数・サイズを記録する。
重要な再現研究で途中状態の実体が必要なら、選んだ時点のsnapshotだけを研究資産として保存する。通常全局へのsnapshot追加は行わない。

**ファイルhashと版が分かること、内容を取り出せること、途中のメモリ状態まで再現できることは別である。**
資産に `availability=included/source_ref/existing_release/hash_only/unknown` を付ける。ディスク上の初期ファイルhashを、対局中に変化したメモリ内容のhashと称しない。
途中状態の完全再現を通常記録の要件にはしない。履歴だけを再生すれば時間制限下の可変Experienceまで完全一致すると保証しない。
既存のBook / Experienceの振る舞いは変えず、観測可能な状態の出所だけを記録する。

## 評価値と指し手を正しく結び付ける
エンジンは着手に採用した**最後の完了結果**に対応する、指し手・評価・完了深さをひとまとまりで出す。対局プログラムはそれをbestmoveと照合し、各手の記録へ格納する。
scoreのcpからmateへの切替や、lower/upper boundからexactへの切替では、前の種別・境界フラグを持ち越さない。終了時の総ノード・最大到達深さは、完了深さとは別に記録する。
現在のarenaはinfoを項目ごとにupdateするため、cpとmateが同時に残る場合がある。実装改修では最新score通知を種別・値・境界の組として扱う。対応が検証できない場合は確定値を作らず `ambiguous` / `not_recorded` とする。
旧データにcpとmateが両方あって通知順を復元できない場合、元の両値を `ambiguous_legacy` として保持する。cpかmateの一方を推測で選ばない。
深さ0、0点、欠損、Bookによる選択をそれぞれ区別する。思考していないBook手に、通常探索の完了を意味する深さを捏造しない。
外部AI側の評価・PV・探索情報を蓄積対象にする方針変更は行わない。

## 研究記録
対象を選んだ局面だけ保存する。実戦アーカイブへの参照（対局ID・何手目の直前か）、開始SFEN＋到達手順、研究ID・日時・目的、Analyzer設定ID、解析時間・制限、選ばれた研究手、評価・深さ・ノード・時間を残す。
着手後の局面を読む研究では評価の視点を明記し、着手者視点へ戻す。別の研究条件・新版の結果も追加記録として残し、旧研究結果を上書きしない。
通常対局で未着手の候補を全収集することと、後日その局面で別の研究手を選ぶことは区別する。
定跡研究では対象局面・相手の実戦応手・手順・適用条件・根拠への参照・確認状態を残す。自動採用はしない。

### 長考研究結果を利用する場合の記録案
`docs/30_長考研究結果の着手への利用案.md` の方式を導入する場合、当時の研究と今回の探索を混ぜない。
研究記録は指定時間上限、実際の総時間、採用した最後の完了結果の時点を区別し、観測できる最終手の安定性も残す。安定性のために候補手全体や探索木を保存しない。
実戦のdecision sourceをresearchとし、研究ID、利用モード、維持・変更の理由を小さく記録する。原研究の時間・評価・深さは参照し、今回の探索時間・ノード・完了深さと別に扱う。
今回の探索が別の手を選んだ場合、その手の評価を採用した研究手の評価として結び付けない。研究利用方式自体は未採用であり、これらの収集も未実装である。

## 保存形式と容量管理
### 形式と保存先
- 開発用ソース・仕様: 通常Git。大量の棋譜データは継続commitしない。
- 長期の実戦記録: gzip圧縮JSONL＋manifest。共通設定・資産はID参照。新形式にはschema版を明示し、schema 1はそのまま読み取り可能にする。
- 長期の研究記録: 実戦とは別の圧縮JSONL。必要局面だけ。
- 長期の正本: GitHub Releasesの月別データ用releaseへrun/attempt/part単位で追記する。毎晩全履歴を再保存せず、データreleaseをEngine製品版のlatest扱いにしない。タグは収集コードを識別し、両対局エンジンのcommitはmanifestに別記する。
- 一時受渡し: Actions artifact。現行圧縮保存は90日要求、古いRawは各workflow設定の期限がある。長期転送の稼働確認前に保存期限を短縮しない。
- 検索索引: 対局後に生成し、元データhashに対応付ける。消えても元記録から再生成できる。検索のたびに全履歴をダウンロードせず、必要な保存単位のみ取得する。

### 容量の確認基準
以下は**運用を見直す目安**であり、GitHubの無料枠・固定上限ではない。
- 通常棋譜と共通情報は、平均 **6KiB/局以内**を初期の設計目安にする。資産実体・研究記録は別計上。超過しても重要な実戦手を自動で間引かない。
- 圧縮ファイルは **256MiB** を超える前に分割する。研究データと資産実体は混ぜず、何が容量を使っているか把握できる形にする。
- 対局後にrunの局数・手数・圧縮bytes・bytes/局・欠損/曖昧件数・新規資産bytesを記録する。
- 保存一覧から累計を集計し、同じhashの資産は一度だけ数える。論理上の重複排除だけでなく、物理的に二重アップロードされた量も別に計上する。
- 一時artifactが **100MiB**、長期保存が **1GiB**、直近の平均が **6KiB/局**を超えたら、増加原因と30日・180日・365日予測を報告して再設計する。長期1GiBは初回点検であり、以後の点検地点と通知のまとめ方はdocs/29に従う。台帳は「通常棋譜・研究記録・知識資産・一時Raw」の内訳を示す。
- 容量対策の順番は、重複物の新規作成防止、再生成できる索引の扱い、診断用Rawの将来の保存期間、研究snapshotの選び方、保存先・圧縮方式の見直し。全実戦手と原評価は保持する。
- 既存データの削除や保存打切りは自動実施しない。閾値超過を理由に保存成功と偽って捨てない。

GitHub Releasesは各asset 2GiB未満、1release最大1000assetsという公表条件がある。ここでは十分小さなファイルへ分割する。公表上の総量上限がないことを、容量管理が不要という意味に使わない。
根拠: https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases
Actions artifactのexpires_atはAPIで確認し、長期保存成功後も元の期限と混同しない。
根拠: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/remove-workflow-artifacts

### 実データでの形式試算
同じ200局・25,989手を使い、schema 2の核となる情報を圧縮する試作を行った。
- 現行schema 1着手アーカイブ: **1,217,210 bytes**（約1.22MB）。
- 核となる試作形式: **444,970 bytes**（約0.445MB、2,224.85 bytes/局）。現行より約63.4%小さい。
- 残したもの: 全実戦手、当時の評価、depth/seldepth、両時間、nodes、長考理由、先後・終局・最終SFEN、出所、既存の共通設定。選択方法が取得できない旧データにはunknownを使った。
- 欠損680手と、cp/mateが同時に残る216手を保った。216手は曖昧として両観測値を保持した。
- 全25,989指し手の一致、評価値の保持、gzip展開後の一致を検査した。
- 新規の確定commit・日時・状態イベント・局ごとの統計等は旧入力にないため、この数字は完成したschema 2の容量ではない。資産実体・研究記録も含まない。

同じ核だけなら1万局で約22.25MB。計画上は6KiB/局として1万局約61.44MB、10万局約614.4MBを見込み、実装後の実測で更新する。増え続ける資産コピーを作らないことが、細かな数値の削減より重要になる場合がある。

## どの仕組みがいつ実行するか
| 時点 | 担当 | 処理 |
|---|---|---|
| build・対局開始前 | 既存Workflow＋対局プログラム | commit・実体・有効設定・知識の初期状態・実行環境を登録 |
| 各着手時 | エンジン＋対局プログラム | 採用結果をUSIで返し、実戦手の小さな行へ対応付け。保存目的の再探索や毎手の資産コピーはしない |
| 一局終了時 | 対局プログラム | 完了局をチェックポイントへ書込み、局ごとの統計と状態イベントを残す |
| 対局バッチ終了・中断後 | 圧縮・検査プログラム＋既存Workflow | 完了局を圧縮し、指し手・手数・出所・欠損・hashを検査。中断局を混同しない |
| 圧縮後 | 既存Workflowの保存処理 | Releasesへ移送し、取得し直したhash一致で保存成功を確定。一時artifactも受渡し・失敗回収用に残す |
| 保存確認後 | 容量台帳・索引生成処理 | bytes内訳・累計・増加を集計し、検索索引を生成 |
| 研究時 | 自作Analyzerを呼ぶ研究処理 | 必要局面を取り出し、研究結果を別記録へ追加 |

同名・同hashの再送は二重保存せず、同名・異hashは上書きせず失敗を明示する。
新しい一回限りのWorkflowを増やす前提にしない。内部比較、位置指定、外部対局等の入口から共通の保存処理を呼ぶ。各入口の自動接続は個別に検証する。

## 実装と検証の完了条件
1. schema 2のwriterとreaderを作り、schema 1からの移行で全実戦手・原評価・曖昧情報・出所が失われないことを確認する。
2. エンジン出力とcollectorを改修し、cp→mate→cp、境界評価→exact、Book手、depth 0、投了で値が前の手・前の種別から混入しないことを確認する。
3. source commitと実体hash、有効設定、資産の復元可否を対応付ける。同じ内容の資産の物理的重複を作らない。
4. 完了局チェックポイントを追加し、途中終了時の完了局の回収を確認する。
5. 既存Workflowから長期移送・hash再確認・容量台帳まで接続し、再送・移送失敗・破損・重複IDを検査する。
6. 初期SFEN＋全手順から局面と先後割当を復元し、過去版・新版で同じ対象局面を取り出せることを確認する。
7. 同じ局面・エンジン・条件で、収集の追加処理時間・メモリと探索深さ/ノードへの影響を測る。圧縮・hash計算・移送・索引生成を探索時間内へ入れない。
8. schema 2の実測bytes/局・資産量を報告した段階で、容量見積りを完成値へ更新する。
