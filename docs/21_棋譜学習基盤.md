# 棋譜学習基盤

## 目的

棋譜学習の前段として、外部棋譜をそのまま評価関数学習へ流さず、**形式変換・重複排除・データ分割・ルール層による全着手検証**を独立した工程にする。

この段階では学習アルゴリズムそのものは実装しない。まず「同じ入力から、同じ学習データを再現できる」ことを優先する。

## 初版の対象

初版はCSA形式を対象とする。

理由は、CSAが機械処理しやすく、手番・移動元・移動先・駒種・成り・持ち駒・勝敗を比較的曖昧なく扱えるためである。KIF/KI2は表記揺れや「同」「成／不成」等の解釈が増えるため、CSA基盤を固めた後に追加する。

対応範囲：

- 平手初期配置 `PI`
- `PI` の駒落ち指定
- `P1`～`P9` の盤面指定
- `P+` / `P-` の持ち駒・配置指定
- `00AL`（残りの駒すべて）
- 通常着手・駒打ち・成り
- 1ファイル内の複数棋譜（`/` 区切り）
- Shift_JIS / UTF-8
- 投了・詰み・時間切れ・千日手・持将棋等の主要終局記録

## 構成

```text
tools/kifu/
  csa.py               CSA -> USI の表記変換
  build_dataset.py     棋譜正規化、重複排除、train/validation/test分割
  validate_games.cpp   やねうら王ルール層で全着手を再検証
  export_samples.py    1局面1教師サンプルのJSONLへ展開
```

CSAパーサは「表記を読む」役割だけを持つ。合法手かどうかの最終判断は行わない。

合法性の正本は従来どおり `engine/rules/Position` である。`validate_games.cpp` は各局面で `legal_moves()` と棋譜手を照合し、合法でなければ学習サンプルを出力せずエラー終了する。

このため、棋譜学習を追加しても「やねうら王から利用するのはルール層だけ」という境界は変わらない。

## データの流れ

```text
CSA棋譜
  ↓
CSA表記をUSIへ変換
  ↓
1局単位の正規化JSONL
  ↓
同一初期局面＋同一指し手列でSHA-256重複排除
  ↓
棋譜単位で train / validation / test に固定分割
  ↓
Positionで初期局面を復元
  ↓
全着手を合法手集合と照合して再生
  ↓
各局面を教師サンプルJSONLへ展開
```

## 重複排除

重複判定キーは、

```text
start_sfen + 改行 + USI指し手列
```

のSHA-256とする。

プレイヤー名、棋戦名、日付、元ファイル名が違っても、初期局面と全指し手が同一なら同一棋譜として1局だけ残す。

## 学習用・検証用の分離

同一棋譜の途中局面が学習用と検証用にまたがると、ほぼ同じ局面を見た状態で検証することになる。そのため**局面単位ではなく棋譜単位**で分割する。

既定値はSHA-256による固定80/10/10分割：

- train: 80%
- validation: 10%
- test: 10%

同じ棋譜・同じsplit saltなら、実行環境や入力順が変わっても同じ集合へ入る。

## 教師サンプル

`export_samples.py` が出力する1行は1局面で、最低限次を持つ。

```json
{
  "game_id": "...",
  "split": "train",
  "ply": 37,
  "position_hash": 123456789,
  "sfen": "...",
  "move_usi": "7g7f",
  "outcome_for_side_to_move": 1
}
```

`outcome_for_side_to_move` は局面手番から見た最終結果：

- `1`: 最終的に勝ち
- `-1`: 最終的に負け
- `0`: 引き分け
- `2`: 勝敗不明・value教師には使わない

これにより、まずは「その局面で実戦棋譜が選んだ手」の教師あり学習に使え、後から勝敗ラベルを用いたvalue学習にも流用できる。

## 使い方

### 1. CSAを正規化

```bash
python3 tools/kifu/build_dataset.py path/to/csa_dir \
  --output build/kifu/games.jsonl \
  --manifest build/kifu/manifest.json \
  --corpus "source-name" \
  --license "usage/license note"
```

### 2. ルール検証器をビルド

```bash
python3 scripts/build.py --kifu-validator --output build/kifu-validator
```

### 3. 学習サンプルへ展開

```bash
python3 tools/kifu/export_samples.py \
  --dataset build/kifu/games.jsonl \
  --validator build/kifu-validator \
  --output build/kifu/samples.jsonl
```

## データ出所とライセンス

棋譜ファイルそのものをリポジトリへ大量投入する前に、出所・利用条件・再配布可否を確認する。

正規化データには `corpus` と `license` を持たせられる。大規模棋譜をGitHubへ直接保存することは想定しない。READMEの既存方針どおり、小規模なテスト棋譜だけGitHubに置き、大量データは必要になった時点で別保存先を決める。

## 現段階でやらないこと

- 評価関数の重みを自動更新すること
- NNUE学習
- 自己対局強化学習
- 定跡として棋譜手をそのまま採用すること
- 外部棋譜をライセンス確認なしに同梱すること

この基盤の次は、実際の棋譜コーパスを少量取り込み、データ品質・重複率・局面数を確認した上で、既存の説明可能な特徴量に対する教師あり重み学習を検討する。
