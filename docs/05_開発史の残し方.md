# 開発史の残し方

このプロジェクトでは、コードだけでなく「なぜ変更したか」「何を試したか」「本当に強くなったか」を後から追えるようにする。

目的は、単なる作業記録ではなく、弱い将棋AIがどのように強くなっていったかを再現できる開発史を残すことである。

# 1. 記録の置き場所

## README.md

現在地の入口。

ここには長い履歴を書かず、

- 現在の到達目標
- 現在のバージョン・状態
- 次にやること
- 主要ドキュメントへの案内

を簡潔に置く。

## docs/

変わりにくい設計・方針を置く。

例：

- 開発方針
- システム構成
- USIの仕組み
- 強化ロードマップ
- 開発史の記録ルール

設計思想や運用ルールを変更した場合は、このフォルダの該当文書を更新する。

## journal/CHANGELOG.md

開発史の索引。

バージョンごとに、

- 日付
- バージョン
- 主な変更
- 強さへの効果
- 詳細journalへのリンク

を短く追記する。

「これまでどう強くなったか」を最短で振り返りたいときは、まずここを見る。

## journal/YYYY-MM-DD_NN_テーマ.md

重要な開発・判断・実験の詳細記録。

毎日の雑談をすべて残すのではなく、後で意味がある単位で作る。

同じ日付に複数のjournalがある場合は、`YYYY-MM-DD_NN_テーマ.md` の `NN` を `01`、`02`…の2桁連番にする。連番は原則として、成果・判断が確定して `main` へ統合された順とする。並行作業は開始時刻ではなく統合順で番号を確定し、一度確定した番号は後から別作業のために振り直さない。これによりGitHubのフォルダ表示だけで同日の開発順を追えるようにする。

記録する内容の基本形：

1. 目的・問題
2. 変更前の状態
3. 仮説
4. 実装した変更
5. 検証条件
6. 結果
7. 判断（採用・保留・撤回）
8. 分かったこと
9. 次の課題

## Gitのコミット履歴

コード・Markdownの正確な変更差分を残す。

journalが「人間が読む開発史」、コミット履歴が「機械的に正確な変更履歴」という役割分担にする。

# 2. 何を開発史として残すか

次のいずれかに当てはまる場合は原則記録する。

- AIの指し手の性質が変わる変更
- 探索・評価関数・合法手生成など主要ロジックの変更
- 旧版との比較対局を実施した
- ユーザーまたは将棋アプリとの節目の対局を実施した
- 強くなった・弱くなったことが測定できた
- 採用しなかった実験でも、後で同じ失敗を避ける価値がある
- 重要な技術選定を変更した
- 再発しそうなトラブルと解決方法が見つかった

軽微な文言修正や単純な整理はjournalを増やさず、コミット履歴だけでよい。

# 3. バージョンの付け方

当面は理解しやすさを優先し、現在は節目ごとに `v0.0.x` を付ける。

例：

- v0.0.1：USIで1手返せる
- v0.0.2：合法手から選べる
- v0.0.3：駒得を評価できる
- v0.0.4：相手の1手先を読める
- v0.0.5：αβ探索を導入

番号は実装前に固定せず、実際の節目に応じて調整する。

大きな到達目標を達成した段階で `v1.0` の扱いを検討する。

# 4. 強化をどう記録するか

「機能を追加した」だけでは強化とみなさない。

可能な場合は旧版と新版を同条件で対局させ、次を残す。

- 対局数
- 先後条件
- 勝敗
- 勝率
- 持ち時間または探索条件
- 平均思考時間
- 探索深さ・探索ノード数（取得できる場合）
- 特徴的な勝因・敗因

ユーザーや既存将棋アプリと対戦した場合は、相手・レベル・条件も残す。

# 5. 開発史の基本原則

- 成功だけでなく、意味のある失敗も残す
- 後から同じ条件を再現できる情報を残す
- journalを細かく作りすぎて読む価値を落とさない
- 数値で比較できるものは数値を残す
- 人間の感想も、数値では分からない「指し味」の情報として残す
- コードと記録が食い違わないよう、重要変更時は同じタイミングで更新する

このルール自体も、開発が進んで不都合が出た場合は改善する。
