# 2026-10-06 対局データ収集の標準化

## 背景

6,520局の遡及Diagnosisから、対局結果を勝敗だけで扱うのではなく、評価急変を入口に「自分の好手」「相手のミス」「両方」「既に強制された悪化」「評価関数の過反応」「探索不足」を切り分ける必要が確認された。

今後の自己対局、旧版比較、Challenger比較、Position Bank再戦、外部benchmarkでも同じ視点を継続利用する。

## 今回の決定

対局データを次の4段階に分離する。

1. Raw Match Record
2. Analysis / Diagnosis
3. Learning Asset
4. Validation

勝った側の手、評価が上がった手、外部AIの手を直接教師ラベルにはしない。

## 実装

### benchmarks/arena.py

全対局で各着手の研究用テレメトリを保存するようにした。

- ply
- side to move
- Engine
- move
- in-check
- legal move count
- capture / promotion / drop
- gave check
- depth / seldepth
- score / mate
- Black-normalized score
- nodes / nps
- PV
- TT probes / hits
- Experience probes / hits
- qnodes / qcutoffs
- elapsed time

telemetry_schema_version = 1 を付与した。

### benchmarks/position_arena.py

Position Bankからのpaired replayにも同じテレメトリを保存する。

### tests/test_arena.py

USI info lineのscore / mate / PV / search stats解析とBlack基準score正規化を回帰テストへ追加した。

### Quick CI

benchmarks/position_arena.py と tests/test_arena.py を監視対象へ追加し、Arena telemetry / adjudication testをCIで実行する。

## 分析・学習設計

正本として docs/26_対局データ収集・分析・学習設計.md を追加した。

全局面を500msで深く読むのではなく、まず全対局を軽量走査し、次を優先して固定Champion Analyzerで再解析する。

- 評価急変
- deep loss候補
- shallow/deep disagreement
- surprise
- static-search gap
- 反復する失敗型
- valuable novelty候補
- unknown

選抜時は同型局面をdedupeし、単純な駒取り・成り・詰み直前が大量重複して上位を占有しないよう、情報価値と多様性を優先する。

## 学習先

- Position Bank
- Problem Suite
- Experience候補
- Book credit候補
- Daytime Research Backlog
- regression test / paired validation

Experience Cacheのnodes・時間削減だけを棋力向上とは判定しない。

## 今後

Nightlyを含む標準runner経由の対局はRaw telemetryを常時保存する。重いDiagnosisと実際のEngine変更は、候補選抜と原因帰属を経た後に行う。
