# v0.0.7：手の並べ替えで3手探索を高速化

## 出発点

v0.0.6で3-plyまで深くした結果、v0.0.5との100局では99勝1敗と大幅に強くなった。一方、同一runの平均応答は225.065ms、最大6.71秒まで増えた。

ここで4-plyへ直進すると計算量がさらに急増する。そこで次の仮説を立てた。

> **探索深さと評価関数を変えなくても、重要そうな手を先に読めばαβが早く枝を切り、同じ答えを少ない局面数で出せる。**

## 実装

`engine/strategy/move_order.h` と `engine/strategy/alphabeta3_ordered.h` を新設した。

優先する手は次の順とした。

1. 王手
2. 高価値駒を取る手。特に飛車・角の捕獲
3. 成る手
4. 相手の飛車・角の長い利きにさらされた自駒を動かす手
5. その他

この順番用の点数は局面評価には足さない。最終判断はv0.0.6と同じ3-ply・同じ駒得評価である。

rootの同点候補は、並べ替える前の合法手順へ戻してからseed付き乱数で選ぶ。これにより、並べ替えだけで同点選択が変わらないようにした。

## 固定テスト

GitHub Actions run `37167431161` で次を確認した。

- 王手優先
- 高価値駒の捕獲優先
- 成り優先
- 飛車・角の利きにさらされた駒の移動優先
- v0.0.6と同じseedで同じ選択手
- 3手目の詰みを維持
- ASan / UBSan
- 既存ルール・USI・独立比較の全回帰

同一4局面での探索ノードは、v0.0.6の52,114に対してv0.0.7は13,594。**約73.9%を削減しながら選択手は完全一致**した。

## 王手優先のテストで見つかった不整合

最初のCIでは「王手が静かな手より先に来る」テストが失敗した。

調査すると、`Snapshot`の契約ではpiece kind 8をKingとしているのに、やねうら王から変換する`Position::snapshot()`では`raw_type_of(KING)`の0をそのまま格納していた。

これまでの駒得評価では玉の点数が0だったため問題が見えなかったが、盤面上の玉を探す王手判定で初めて表面化した。

`type_of(pc) == KING`の場合だけ明示的にkind 8へ変換するよう修正し、自作APIの契約と実装を一致させた。ルール判定や駒価値を変更したものではない。

理由：

- 3-ply深さと駒得評価を変更していない
- 同一seedでv0.0.6と同じ選択手を確認
- 3手目の詰みを維持

- 正式100局で探索ノード約82.3%削減

- 全回帰、Sanitizer、Androidビルドを通過

## 次の課題

今回の結果から、CPU性能を上げるだけでなく**探索順を工夫するだけでも大きな速度改善が得られる**ことが具体的に確認できた。

次はすぐ4-plyへ進むのではなく、次の候補を比較する。

- 置換表：同じ局面を何度も読み直す無駄を減らす
- 反復深化：浅い探索で見つけた良い手を次の深さで先に読む
- move orderingの改善：過去に良かった手、捕獲の効率などを利用する
- 時間管理：局面ごとの最大思考時間を制御する

これらでさらに余裕を作ってから4-plyへ進む。
